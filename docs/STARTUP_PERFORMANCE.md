# 시작 성능 계약

목표는 **프로세스 시작부터 실제 조작 가능한 주 화면까지 2,000ms 이하**다.
빈 창, 로딩 표시, 백엔드 준비 완료만으로 달성 판정하지 않는다. Windows가
시작 프로그램을 늦게 실행하는 시간은 앱 내부 시간과 별도로 기록한다.

## 준비 순서

1. 기존 변경은 v1.8.0 / 91ae690으로 커밋·푸시·배포했다.
2. 프로세스 진입, UI setup, 첫 화면 응답, 설정, DB 복구, 녹화 저장소,
   작업 재개를 별도 구간으로 기록한다. 측정 기록에는 작품·채널·경로·키를 넣지 않는다.
3. JSON 파일은 기존 크기 제한과 일반 파일 검증을 유지하며 버퍼링해서 읽는다.
4. 파일 복구와 녹화 이력 초기화는 UI 이벤트 루프 밖에서 실행한다.
   준비 중인 기능은 대기 상태를 명시하고, 탐색 입력·탭 전환·종료 UI는 응답한다.
5. 녹화 이력 준비가 Hitomi 사용을 막지 않게 서비스 준비 상태를 분리한다.
   초기화 도중 종료·초기화를 요청해도 늦게 도착한 서비스가 작업을 재개하지 않는다.
6. 다운로드는 병합 복구 → 격리 이동 정합성 확인 → 재개 순서를 보존한다.
   이 순서를 우회해 속도를 얻지 않는다. 기존에 읽은 앨범 캐시도 제거하지 않는다.
7. 첫 화면에 필요 없는 전체 목록 조회·유지보수·이미지 예열은 뒤로 미룬다.
8. 과거 완료/중지 녹화는 시스템 드라이브의 폐기 가능한 요약 인덱스를 읽는다.
   목록에는 `마지막 저장 상태`라고 표시하며, 재생·삭제·재병합·기록 변경 전에
   인덱스의 해당 항목을 먼저 영구 무효화하고 원본 저널을 다시 검증한다.
   미완료 녹화·미완성 파일·병합 및 정리 대기 항목의 원본 검증은 생략하지 않는다.
   과거 항목 복구는 시작 20초 후부터 백그라운드에서 한 건씩 수행한다. 이는
   Windows가 과거 영상 전체를 앱 시작에 필요한 파일로 예측하지 않게 하는
   과거 작업 전용 유예다. 새 자동녹화·새 구간 병합·명시적 재생/재시도는 기다리지 않는다.
   인덱스는 파일 접근이나 삭제 권한의 근거가 아니며, 손상 시 원본 복구로 돌아간다.

## 측정과 합격 조건

- release 빌드, 실제 규모의 데이터, 반복 실행 및 재부팅 후 최초 실행을 구별한다.
- 시작 시각은 Windows 프로세스 생성 시각을 포함한다. UI 측정은 첫 렌더 이후
  이벤트 루프 왕복을 확인하고, 실제 입력·탭·종료 응답도 검증한다.
- 정상 종료, 초기화 중 종료, 이전 작업 복구, 녹화 저장 장치 지연/부재,
  오프라인 및 초기화 오류에서 데이터와 종료 경로를 검증한다.
- 느린 장치 준비는 별도 상태로 남긴다. 실제 화면이 멎은 시간을 제외하거나
  타이머 시작을 늦추어 2초로 보이게 하지 않는다.
- 현재 측정 기준: 기존 1.7.0 실제 프로필 재실행의 DB 준비→백엔드 준비 약
  16.6초. 녹화 메타데이터 229개 파싱 실험은 같은 데이터에서 비버퍼 약
  1,442ms / 버퍼 약 12ms였으며, 이는 전체 시작 시간 결과가 아니다.

## Windows 시작 지연 분리

2026-09-20 실제 프로필의 최적화 중간 빌드에서, 기본 실행 파일은
프로세스 생성→최초 Rust 코드까지 5.6~13.6초가 걸렸다. 이후 조작 가능한
화면까지의 앱 작업은 약 0.7~0.9초였다. OS 추적에서도 첫 스레드가 앱 코드를
실행하기 전에 약 7.7초 대기했다. 별도 이름의 바이트 단위 동일 실행 파일은
715ms였으므로 이름만 바꾼 결과를 합격 판정에 사용하지 않았다.

Windows의 기존 Atsumi 시작 예측 기록에 녹화 저장 드라이브 파일 수백 개가
포함돼 있었다. 현재 release 경로의 예측 파일 **한 개만 백업 이동**한 후,
같은 이름·경로·실행 파일로 최초 코드 진입 14ms, UI 입력 준비 696ms가 나왔다.
시스템 전체 캐시, SysMain, 보안 설정은 변경하지 않았다. 녹화 요약 인덱스는
같은 대량 디스크 읽기를 다음 시작 예측에 다시 학습시키지 않기 위한 구조 개선이다.

다만 중간 빌드의 후속 실행에서는 기존 녹화 복구를 다시 시작 구간에 읽으며
프로세스 생성부터 입력 준비까지 7,787ms, 실행 요청부터는 12,827ms가 걸렸다.
최종 빌드는 이 복구를 지연시키도록 수정했지만 아직 실제 실행을 측정하지 않았다.
설치본을 포함한 예측 기록 재학습의 두 번째 관리자 승인 요청은 취소되어 적용하지
않았다. 696ms 한 번만으로 반복 실행·부팅 직후의 목표 달성을 주장하지 않는다.

## 검증 현황

### Atsumi 전용 Prefetch 실행 시나리오

- 일반 release와 자동 실행은 고정된 `/prefetch:1`, 개발 런처는 `/prefetch:2`를
  실제 Atsumi 프로세스에 전달한다. 기존 인자 없는 실행 기록과 분리하며 번호를
  실행마다 바꾸지 않는다. 일반/자동 실행은 같은 앱 동작이므로 같은 번호를 쓴다.
- 이는 Windows ALPF 학습 시나리오 선택일 뿐, SysMain 비활성화나 썸네일/파일
  캐시 차단이 아니다. Windows Prefetch 파일 삭제와 레지스트리 변경도 하지 않는다.
- 현재 바탕화면 release와 기존 자동 실행 바로가기는 명시적으로 선택한 대상만
  백업 후 인자를 갱신한다. 자동 실행을 새로 켜거나 Windows의 허용 상태를 바꾸지 않는다.
- 실행 파일을 탐색기에서 직접 더블 클릭하면 인자가 없으므로 이 분리를 사용하지
  않는다. 기존 설치 관리자가 새로 만드는 링크 역시 별도 적용 전에는 보장하지 않는다.
- `tools/set_app_prefetch_shortcut.ps1`은 대상 확인·백업·동시 변경 확인 후 원자적으로
  교체한다. 다른 앱, 사용자 지정 인자, 리다이렉트된 바로가기는 수정하지 않는다.
- 검증은 임시 바로가기와 명령 인자 검사로 수행한다. 실제 앱 실행/성능 재측정은
  사용자에게 맡기며, 이 분리만으로 2초 시작을 보장하지 않는다.
- 적용 확인: 바탕화면 release와 기존 자동 실행 링크 모두 `/prefetch:1`을 읽어
  확인했으며 원본 링크·실행 파일은 `.runtime/prefetch-scenario-backups`에 보존했다.
  로컬 release 빌드와 설치본 SHA-256은
  `5e32f036e5e227c9abb8e981e648319f1d2179cc04d220d07157b9241ca4030f`로 일치한다.
- 이번 검증: 자동 실행 Rust 테스트 10개, 바로가기 백업/WhatIf/반복 적용/메타데이터
  보존/사용자 인자 및 다른 앱 거부/런처 구문 검사 통과. release 빌드 성공.
  변경한 Rust 파일의 fmt와 diff 검사는 통과했다. 전체 fmt는 다른 작업의 녹화
  복구 파일들에 형식 차이가 있어 미통과했으며 해당 파일들은 수정하지 않았다.

### 기존 시작 최적화 검증

- 시작·종료·파일 복구 포함 Rust: library 815, main 2 통과 / 20 opt-in ignored.
- clippy all-targets: 경고를 오류로 처리한 검사 통과.
- frontend: 117개 파일, 1,155개 테스트 통과. 샌드박스에서 Edge GPU 실행이
  거절됐던 레이아웃 검사는 정상 권한의 격리 프로필로 재실행해 통과했다.
  이후 추가한 녹화 요약 상태 회귀 테스트를 포함해 RecordingLibrary 18개도 통과했다.
- 최종 로컬 release 실행 파일 빌드 성공. 공개 v1.8.0 배포물은 덮어쓰지 않았다.
  설치 경로의 중간 빌드는 별도 백업 후 최종 실행 파일로 교체하고 SHA-256 일치를
  확인했다. 바탕화면 release 대상과 자동 시작 대상 모두 최종 로컬 빌드를 사용한다.
  교체 후 앱을 실행하지는 않았다.
- 중간 빌드 실제 화면: 시작 안내 닫기, 설정 열기, 정상 종료 응답 확인.
- 설정 점검 중 다중 WebView 환경에서 자동 실행 설정 IPC가 실패하는 것도 수정했다.
- 2026-09-20 사용자 요청으로 Computer Use와 실행·재부팅 검증을 중단했다.
  반복 실행 및 재부팅 후 최초 실행 검증은 남아 있으며, 전체 목표 달성 판정은 보류한다.

재현 도구: `tools/measure_startup.ps1`. 앱이 이미 실행 중이면 중단하며 자동으로
프로세스를 종료하지 않는다. 실행 요청→프로세스 생성→입력 준비 시간을 함께
출력하고, 실제 창은 UI 확인을 위해 열린 채로 둔다. 로그와 OS 추적은 로컬에만
보관하며 업로드하지 않는다.
