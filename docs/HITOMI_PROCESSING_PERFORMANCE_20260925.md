# Hitomi 다운로드 후처리 성능 개선 — 2026-09-25

## 범위와 원칙

활성 개발 폴더는 `2849/Atsumi Project`다. `3b2a` 백업, 기존 다른 작업,
사용자 앨범/녹화/즐겨찾기 데이터는 수정하지 않는다. 커밋·푸시·릴리즈는 요청되지 않았다.

파일 SHA-256 무결성 확인, 중복 판단 임계값, 포함관계 우선 규칙, 작가 단위 최종 판정
직렬화, 자동 제외 전 재검증을 유지한다. 전체 라이브러리 재검사는 시작하지 않는다.

## 확인한 병목

- 네트워크 다운로드가 끝나도 해시/비교 후처리가 완료되지 않으면 목록은 `hashing`으로 남는다.
- 최종 처리 작업자는 2개이고, 각 앨범 페이지 해시는 직렬로 계산했다.
- 1,024비트 상세 해시 문자열을 페이지 조합마다 다시 해석했다. 중앙 영역 계산은 같은 바이트를
  비트마다 다시 문자열로 해석했다. 큰 앨범끼리 대조하면 이 비용이 페이지 수의 곱으로 증가한다.
- 지각 해시의 고정 코사인값을 페이지마다 다시 계산했다.
- SHA 재검증과 HDD 읽기 보호 대기는 별도 비용이다. CPU 병렬화만으로 모든 대기가 사라지지는 않는다.

## 구현

1. 상세 해시를 앨범 비교당 페이지별로 한 번만 정수로 변환한다. 전체/중앙 거리 계산은 동일한
   비트 영역의 XOR와 비트 수 집계로 수행한다. 대조 결과와 기존 판정 기준은 바꾸지 않는다.
2. 지각 해시의 코사인 표를 프로세스에서 재사용한다. 곱셈·누적 순서까지 유지해 기존 캐시와 호환한다.
3. `설정 → Hitomi → 고성능 처리 모드`를 추가했다. 기본값은 OFF다.
   - OFF: 기존 공유 이미지 처리 2슬롯, 앨범별 직렬 해시 처리.
   - ON: 페이지 해시 및 대조 행을 병렬로 처리한다.
   - 동시 처리 상한은 논리 프로세서 수에서 2개를 뺀 값, 메모리 예산, 16개 중 최솟값이다.
   - 메모리는 총 RAM의 1/4 또는 설정 적용 시 가용 RAM의 1/2 안에서 작업당 512MiB로 계산한다.
     하드웨어 정보를 읽을 수 없으면 보수적으로 제한한다.
   - 현재 PC는 Ryzen 7 5800X, 논리 프로세서 16개, RAM 약 32GiB이므로 메모리 여유가 있으면 최대 14개다.
   - 여러 앨범이 동시에 처리돼도 공유 처리 상한을 중복 적용하지 않는다.
   - 설정 저장 시 공유 상한을 변경한다. 이미 만들어진 작업 묶음은 안전하게 마치고, 다음 묶음부터
     새 병렬 수를 사용한다. 모드를 끄면 이미 시작한 계산을 강제 종료하지 않고 대기 작업을 제한한다.
4. 병렬 결과는 원래 페이지 순서로 모은다. 오류 시 새 작업 배정을 멈추고 진행 중인 작업을 합류시킨 뒤
   최초 오류를 반환한다. 취소 신호와 기존 해시 캐시 키를 유지한다.
5. HDD 해시 읽기는 단일 읽기 슬롯과 기존 볼륨별 24MiB/s 보호 예산을 사용한다. 서버 요청 수와
   서버의 대기 요구는 변경하지 않는다. 모드가 오버클럭이나 OS 전원 설정을 바꾸지는 않는다.
6. 후처리 로그에 페이지 수, 캐시 적중 수, 작업 수, 해시 시간, 후보 검증 시간, 비교 시간을 추가했다.

## 의도적으로 생략하지 않은 검사

후보 파일의 전체 SHA-256 재검증은 그대로다. 과거 해시가 있다는 이유만으로 현재 파일이 같은지
확인하지 않고 자동 제외하면, 외부 수정·병합·손상을 놓칠 수 있기 때문이다. 향후 읽기 캐시 최적화는
현재 파일과 검증 증거를 안전하게 연결하는 별도 설계가 필요하다.

## 측정

사용자 파일이나 네트워크를 사용하지 않는 합성 데이터, 현재 개발 빌드에서 단독 실행했다.

| 계산 구간 | 기존/직렬 | 개선/병렬 |
| --- | ---: | ---: |
| 상세/중앙 해시 거리 32,400쌍 | 1,142ms | 6ms |
| 640×960 이미지 48장 해시 | 직렬 15,748ms | 14개 병렬 1,952ms |

두 방식의 결과가 같음을 함께 검사했다. 약 190배/8배는 각각의 CPU 계산 구간 수치이며,
전체 다운로드나 HDD 포함 완료 시간의 배율이 아니다. 전체 실사용 시간은 새 단계별 로그로 확인해야 한다.

## 검증 및 인계

- 네이티브 전체 회귀 검사: 889개 통과, 26개 명시적 opt-in 검사 제외, 실패 없음.
- 설정/API/앱 연동 프런트엔드 테스트: 142개 통과.
- 정식 TypeScript 프로젝트 빌드 검사와 Vite UI 빌드 통과.
- 상세 거리 모든 1,024비트, 혼합/대소문자 해시, 기존 DCT 계수 비트 동등성 검사 통과.
- 병렬 출력 순서·작업자 상한·실패 시 합류·취소 대기·동적 상한 변경을 검사했다.
- 전체 프런트엔드 검사: 1,262개 통과, 10개 실패. 이번 변경 범위 밖의 추가 발견 사항이다.
  - CHZZK 실제 화면 배치 9개: Edge 테스트 프로세스가 DOM/측정값을 반환하지 않는다.
    대표 4개를 단독 재실행해도 동일했다.
  - CommunityNavigation 1개: 활성 탭이 `새 탐색`인데 기존 테스트는 작품 제목을 기대한다.
    단독 실행에서도 재현된다. 이 작업에서 해당 제품 동작/테스트 기대값을 임의로 바꾸지 않았다.
- 마지막 컴파일 과정에서 rustc 증분 캐시 내부 오류가 발생했다. 해당 프로젝트 캐시 2개만
  `.runtime/compiler-cache-recovery-20260925`에 보존 이동했다. 소스·DB·앨범은 변경하지 않았다.
- 개발 앱은 진행 중 다운로드와 녹화가 없는 상태를 확인한 후 빌드 전 중지했다.
  마지막 다운로드 완료 로그는 KST 01:02:58이었다.
- 개발 실행 파일(`src-tauri/target/debug/atsumi.exe`) 최종 빌드 완료.
  바탕화면 `Atsumi (디버그).lnk`는 개발 런처, `Atsumi (릴리즈).lnk`는 설치된 릴리즈다.
  이번에는 릴리즈를 갱신하지 않았다. 다음 실행은 디버그 바로가기를 사용한다.
- 사용자가 요청한 PC 종료는 저장되지 않은 다른 앱을 강제로 버리지 않는 Windows 종료 요청으로 수행한다.
