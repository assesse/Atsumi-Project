# 다운로드 요청량 조정

## 2026-09-10 소규모 실측

개인 다운로드 기록 대신 사이트 공개 `index-all.nozomi`의 첫 항목을 표본으로 사용했다.
이미지는 표시·해독·저장하지 않고 HTTP 본문만 읽어 버렸다. 사용자 DB는 변경하지 않았다.

- 공개 표본 ID: `4180618`, 동일한 앞 5개 파일, 묶음당 599,428 bytes.
- 동시 요청 순서: `1 → 3 → 2 → 5 → 5 → 2 → 3 → 1`.
- 시작 간격 최소 25ms, 묶음 간 2초 대기. 이미지 요청 총 40회, 총 4,795,424 bytes(약 4.57MiB).
- 40회 모두 HTTP 200. 429/503 및 요청량 한도 헤더는 관찰되지 않았다.
- 시험 상한: 동시 5개, 이미지 40회, 전체 64MiB, 파일당 4MiB. 오류 즉시 중단, 재시도·다른 호스트 대체·리다이렉트 없음.

| 동시 요청 | 1차 / 2차 묶음 시간 | 평균 |
| --- | --- | --- |
| 1 | 2.653 / 1.167초 | 1.910초 |
| 2 | 0.982 / 0.682초 | 0.832초 |
| 3 | 0.784 / 0.528초 | 0.656초 |
| 5 | 0.853 / 0.378초 | 0.616초 |

이 표본에서 5개는 2개보다 전송 시간이 약 26% 짧았다. 단일 앨범의 작은 파일 5개를 반복한 결과이며 연결 재사용, CDN 캐시, 순간 지연의 영향을 받는다. 큰 원본·지속 다운로드·이미지 변환·디스크 쓰기·중복 검사를 포함한 앱 전체 성능을 뜻하지 않는다. **공식 허용량이나 서버 최대 한도를 알아낸 시험이 아니다.** 기존 HTTP 기본 상한인 5개까지만 비교했다.

## 실사용 학습 정책

위 실측 이후, 추가 시험 트래픽 없이 **평소 다운로드만 관찰하는 학습**을 추가했다. 현재 앱의 안전 상한은 8개이며 서버가 허용한다고 확인한 숫자가 아니다.

- 새 기록이 없으면 `min(5, 기존 동시 이미지 요청 값, 자동 조절 최대 요청)`에서 시작한다. 자동 조절은 기본 켜짐, 최대값은 기본 8이며 1~8에서 설정한다.
- 일반 미리보기/메타데이터는 기존 요청 설정과 우선순위를 유지한다. 다운로드만 별도 학습 범위에서 늘어난다. 앨범 작업자는 최대 8개를 공급하지만 HTTP가 현재 학습값에 따라 실제 전송 수를 제한한다.
- 끄면 다운로드 작업자는 기존 요청 값과 8 중 작은 값으로 고정한다. 기존 호스트별 상한, 서버 대기와 감속은 유지한다. 설정은 앱 재시작 후 적용된다.
- 이미지 해독·변환·중복 해시는 공유 슬롯 2개를 유지한다. 슬롯은 HTTP 본문을 받기 전에 점유하지 않는다.

### 증가와 검증

1. 같은 요청 수에서 **2분 이상, 성공한 이미지 60개 이상, 16MiB 이상**을 모은다. HTTP 큐 대기는 네트워크 서비스 시간에 포함하지 않는다.
2. 관측의 60% 이상에서 요청 용량이 사용 중이거나 다운로드 대기가 있어야 한다. 이미지 처리 적체 관측은 20% 이하여야 하며 실제 저장 진척도 있어야 한다. 미리보기·메타데이터는 학습 표본에 넣지 않는다.
3. 조건이 충족되면 **1개만 늘려** 같은 길이의 관측을 다시 한다.
4. 전송 처리량이 **8% 이상 개선**, 평균 요청 지연은 기존의 **125% 이하**, 실제 페이지 저장 처리량은 기존의 **95% 이상**일 때 새 값을 채택한다. 평균 파일 크기가 절반~두 배 범위를 벗어나면 비교 불충분으로 본다.
5. 개선이 없거나 표본/수요가 부족하면 이전 값으로 복귀하고 **15분간 재증가를 보류**한다. 시험값은 안정값으로 저장하지 않는다. 채택 후에도 다음 증가 전 새 기준 관측을 모은다.

30초 넘게 요청이 끊기면 시험 관측을 버린다. 조정 전에 시작한 응답은 새 관측에 섞지 않으며, 늦게 도착한 일반 오류가 새 시험을 잘못 취소하지 않도록 요청 세대를 확인한다.

### 감속과 서버 대기

- 429/503이면 호스트 요청 수와 자동 다운로드 수를 절반(최소 1개)으로 줄인다. 호스트 요청 간격도 최소 100ms에서 최대 2초까지 늘리되 더 느린 사용자 설정은 보존한다.
- 다운로드 전체와 해당 호스트의 요청은 `Retry-After` 동안 기다린다. 초/HTTP-date를 처리하고 5분으로 자르지 않는다. 긴 대기도 취소할 수 있다. 다른 이미지 후보/호스트로 전환해 대기를 피하지 않는다.
- 3회 연속 전송 오류/시간 초과는 자동 다운로드 수를 절반으로 줄인다. 시험 중 일반 오류는 시험값을 철회한다.
- 두 관측 구간 연속으로 심한 이미지 처리 적체가 발생하거나, 비교 가능한 파일들에서 처리량이 25% 이상 떨어지고 지연이 25% 이상 늘면 1개 줄인다. 재증가는 15분 보류한다.
- 호스트 자체의 감속은 대기가 끝난 뒤 30초/성공 30회 기준으로 설정 상한 안에서 서서히 회복한다. 다운로드 전체의 증가는 위의 실제 성능 검증을 별도로 통과해야 한다.

### 로컬 저장

Migration 45가 기존 요청 설정을 보존하면서 새 옵션과 `download_tuning_profiles`를 추가한다. Hitomi CDN 전체의 최근 안정값/감속값, 기준 처리량, 관측 시각, 증가 보류/대기 종료 시각을 요약 저장한다. 실제 호스트별 서버 대기 시간도 별도 행으로 남긴다. 앨범 ID, URL, 다운로드 내용은 저장하지 않는다.

확인되지 않은 시험값은 저장하지 않는다. 재시작 시 안정값을 현재 최대 설정에 맞춰 복원하고, 7일 넘은 성능 기록이나 시계 역행으로 미래가 된 기록은 시작값으로 재평가한다. **서버 대기 시간은 성능 기록 만료·시계 역행·자동 조절 해제와 별개로 보존**한다. SQLite 저장은 스케줄러 잠금 밖에서 수행하고 오래된 동시 저장이 새 관측을 덮어쓰지 않도록 한다. 저장 실패는 다운로드를 실패시키지 않고 내부 로그에 남긴다.

공유 슬롯은 다운로드의 무거운 이미지 작업 개수를 제한한다. 더 많은 작업자가 압축 응답을 보유할 수 있으므로 **전체 RAM 1GB의 절대 상한을 보장하지는 않는다**. 최대 8개는 이 위험을 제한하는 초기 앱 상한이다. 이번 구현 작업에서는 사용자 DB·기존 실행 파일을 바꾸거나 추가 실서버 측정을 하지 않았다.

## 검증과 수동 진단

일반 회귀 테스트는 로컬에서 실행하며 외부 서버에 요청하지 않는다. 수동 측정기는 별도 opt-in 예제로만 제공한다.

- `cargo test --locked --all-targets --quiet`: library 450개 + main 2개 통과, 14개 opt-in 테스트 제외, 실패 없음.
- 전체 frontend: 76 files / 592 tests 통과. 앱/Node TypeScript 검사와 Vite production build 통과.
- `cargo fmt --check`, `git diff --check`: 통과.
- 엄격 Clippy는 기존 `overlap_merge.rs`의 3개 경고(`drop_non_drop`, `manual_contains`, `bool_assert_comparison`) 때문에 실패한다. 이 작업에서는 해당 파일을 수정하지 않았다.

```powershell
cd src-tauri
cargo run --locked --example measure_hitomi_transport -- --public-sample
```

반복 실행은 새 외부 요청을 발생시키므로 CI나 앱 시작 시 자동 실행하지 않는다. 제한을 소진하거나 최대 한도를 찾기 위해 반복 실행하지 않는다.

HTTP 규약: [429 응답](https://www.rfc-editor.org/rfc/rfc6585.html#section-4), [Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3).
