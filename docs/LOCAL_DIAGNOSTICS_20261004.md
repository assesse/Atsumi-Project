# 로컬 기본 진단과 즐겨찾기 단순화

2026년 10월 4일 요청에 따라 기본 진단과 용량 제한이 있는 순환 로그를 구현한다. 로그는 해당 PC에만 남는다. 원격 접근, 자동 전송, 진단 파일 내보내기, 상세 문제 재현 모드는 이번 범위에 포함하지 않는다. 기존 데이터와 녹화 파일은 변경하지 않는다.

## 기록 범위

네이티브 앱의 INFO·WARN·ERROR 이벤트는 코드 모듈과 줄 번호로 기록한다. 메시지 전체를 저장하지 않고 허용한 필드만 복사한다. 따라서 새로운 오류가 발생해도 해당 코드에 기존 로그가 있다면 위치를 찾을 수 있다.

- 시작 단계와 경과 시간, 정상 반환·시작 실패, Rust panic의 소스 파일명과 줄 번호.
- 주요 검색·다운로드·즐겨찾기·커뮤니티 작업의 시작·종료와 성공 여부. 작업 식별자는 실행 중에만 대응되는 임시 값이다. `operation_closed`는 성공 표시가 아니며 결과 이벤트를 따로 확인한다.
- Hitomi 수신과 최종 처리의 연결, 작가 잠금 대기, 파일 검증, 판본 비교, manifest 저장 단계. 기존 작업·상태 전이 로직은 바꾸지 않는다.
- 네트워크 요청 수·실패 수·시간 집계와 실패 HTTP 상태. transport 오류는 timeout·connect·redirect·body·decode·기타로 구분한다. connect만으로 DNS와 TLS 중 원인을 확정할 수는 없다.
- 주 DB의 50ms 이상 SQL 실행과 mutex 대기. SQL 문장과 바인딩 값은 저장하지 않는다.
- UI 응답 지연·메모리·긴 프레임, 문서 다시 로드와 복구 판단, 렌더러 실패, 프런트엔드 오류·처리되지 않은 Promise·React 오류 발생 사실. 프런트엔드 메시지와 stack은 복사하지 않는다.
- 자동녹화 상태 변경, 녹화 병합의 코드 위치와 소요 시간, 녹화 수신 처리 지연·실패. 정상 미디어 패킷은 표본만 남긴다.

검색어, 작품 제목·번호, 태그 내용, 닉네임, 댓글·채팅, 로그인 쿠키·토큰, URL·쿼리, 사용자 파일 경로, 미디어 본문, DB 전체를 새 기본 로그에 복사하지 않는다. 기존 콘솔용 자유 형식 로그는 진단 공유 대상으로 간주하면 안 된다.

## 저장과 제한

새 공통 로그의 위치는 `%LOCALAPPDATA%\Atsumi\Logs\diagnostics\application-0.jsonl`부터 `application-3.jsonl`까지다. 한 파일은 4MiB, 합계는 16MiB다. 다음 오래된 슬롯만 교체하고, 재실행 시 가장 최근 슬롯 뒤에 이어 쓴다. 정해진 일수를 보장하는 방식이 아니라 기록량에 따라 남는 기간이 달라지는 방식이다.

디스크 쓰기는 전용 스레드가 담당한다. 최대 256개 기록만 대기시키며 큐가 가득 차면 호출자를 기다리게 하지 않고 누락 횟수를 센다. 일반 HTTP 성공은 5초 단위로 집계한다. 파일 쓰기와 별도로 주기적으로 디스크 동기화를 시도하고, 정상 종료 시 최대 500ms만 마지막 기록을 기다린다. 전원 차단 직전의 모든 기록까지 보장하지는 않는다.

기존 UI 상세 진단은 별도의 2MiB 파일 세 개를 계속 사용한다. 기존 시작 로그도 별도로 유지한다. 이전 CHZZK의 실행별 `capture-*.jsonl` 파일은 삭제하지 않지만, 새 녹화 기본 진단은 공통 순환 로그를 사용하므로 같은 영구 파일을 매 실행 추가하지 않는다. 사용자 DB·다운로드·녹화·기존 로그를 일괄 청소하지 않는다.

다른 프로세스가 동일한 로그를 쓰고 있으면 두 번째 기록기를 열지 않는다. 로그 폴더를 만들거나 쓰지 못해도 앱의 원래 작업은 계속된다. 기록 공백이나 누락 수가 있으면 해당 시간대에 문제가 없었다고 단정하면 안 된다.

## 남는 한계

기록하지 않은 과거 내부 상태는 복원할 수 없다. 프로그램 진입 전 Windows 로더 오류, 메모리 전체 내용, 개별 SQL 문장, 사이트 응답 본문은 포함하지 않는다. 앱이 강제 종료되면 정상 종료 이벤트가 없을 수 있지만, 그것만으로 강제 종료와 전원 차단을 구별할 수는 없다. 특정 PC의 문제가 기본 기록만으로 설명되지 않으면 별도 계측과 재현이 필요하다.

후속 진단 파일 기능은 이 기본 로그를 바탕으로 사용자 확인 후 내보내는 방식이어야 한다. 현재 파일을 자동 수집·전송할 권한이나 서버는 추가하지 않았다. 기존 `control-endpoint.json`, 탐색 체크포인트, 인증 저장소, 녹화 원본 등은 통째로 묶지 않는다.

## 카드 선택과 내 즐겨찾기

Explore·Auto Find·Downloads의 상세·요약 카드는 공통 컴포넌트를 쓴다. 한 장 클릭은 강조만 하고 체크 버튼을 만들지 않는다. 두 장 이상 선택할 때만 체크 버튼을 만들며, 다시 한 장이 되면 제거한다. 더블클릭은 상세보기로 이어진다. 기존 코드에도 동일한 조건이 있었으며 이번에는 여섯 가지 탭·표시 조합을 회귀 테스트한다. 배포된 실행 파일은 새 소스를 빌드하기 전까지 바뀌지 않는다.

내 즐겨찾기는 앨범·페이지 두 분류만 남긴다. 컬렉션 옆 목록, 생성·이름 변경·삭제 메뉴, 책갈피 옆 드롭다운과 해당 스타일을 제거한다. 목록 조회는 항상 컬렉션 필터 없이 실행하므로 예전에 분류했던 항목도 그대로 보인다. 이전 버전과의 호환 및 데이터 보존을 위해 DB의 과거 분류 정보와 호환 API는 파괴하지 않는다. 등록·해제, 검색, 페이지 위치 열기, 우클릭 상세보기는 유지한다.

## 무설치 배포 검토

ZIP을 풀어 실행하는 버전을 주 배포로 삼는 것은 가능하다. 현재 코드의 녹화 도구 리소스도 포함한 ZIP을 구성하고, 설정·DB·작성자 키는 기존 AppData 위치에 유지하는 방식을 우선 권장한다. 설치 과정 없이 실행하는 것과 모든 데이터를 USB 폴더에 넣어 다른 PC로 옮기는 것은 다른 요구다. 후자는 Windows 보호 키와 로그인 정보의 이동 정책까지 따로 설계해야 한다.

현재 릴리즈 도구와 자동 업데이트는 NSIS 설치 파일용이다. 따라서 무설치 메인 전환에는 ZIP 검증, 실행 중 파일 잠금·녹화 보호를 포함한 업데이트 교체, 앱 폴더 이동 후 바로가기·자동 실행 경로 처리, WebView2 의존성 안내가 필요하다. 설치 버전은 기존 사용자의 업데이트를 위해 보조 배포로 유지할 수 있다. 이번 요청에서는 가능 여부만 검토했으며 배포 방식이나 설치본을 변경하지 않았다.

Tauri의 Windows updater는 MSI·NSIS 아티팩트를 기본으로 설명하며, WebView2가 없는 PC에 대한 배포도 고려해야 한다. [Tauri updater](https://v2.tauri.app/plugin/updater/), [Microsoft WebView2 배포](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution).
