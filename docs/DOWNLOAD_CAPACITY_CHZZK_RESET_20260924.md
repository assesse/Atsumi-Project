# 다운로드 일괄 재시도와 CHZZK 초기화 점검 (2026-09-24)

## 다운로드 수정

- 기존 200개 제한은 대기열 전체 제한이 아니라 IPC 요청당 ID 개수 제한이었다.
- 사용자가 앱을 종료한 뒤 읽은 DB에는 active 상태가 12개(해시 검사), interrupted 1,511개, failed 6개였다. 이 값은 실행 중 작업자 수가 아니라 저장된 상태다.
- Downloads의 `전체 다운로드`는 현재 필터의 재시도 가능 항목 중 대기·진행 합계 200개에 남은 자리만 채운다. active에는 queued, resolving_metadata, downloading, hashing, verifying, retry_wait를 포함한다.
- 12개 진행 중이라면 최대 188개 추가한다. 이미 200개 이상이면 기존 작업을 취소하거나 이동하지 않고 추가만 하지 않는다.
- 네이티브 `ManagedWorkGate` 안에서 수량 확인 → 재시도 상태 변경 → 작업자 큐 등록을 수행한다. 다른 UI 요청과 같은 여유분을 중복 소비하지 않는다.
- 요청 자체도 200개 이하로 제한한다. 추가되지 않은 항목은 그대로 남으며, 대기열이 줄어든 뒤 사용자가 다시 요청한다. 자동 보충 기능은 아니다.
- 반복 클릭을 막고, 실제로 접수된 항목만 활동 기록에 추가한다. Explore/Auto Find 및 개별 재시도의 기존 계약은 유지한다.
- 실사용 다운로드를 대신 시작하거나, 히토미 DB/즐겨찾기/앨범을 정리하지 않았다.

## CHZZK 삭제 전 확인한 사실

원시 로그를 보존하는 대신 집계 및 코드 분석 결과만 이 문서에 남긴다.

- 브라우저 방식 녹화 이력 308개. 이 중 226개는 종전 요청에 따라 영상만 삭제하고 진단 이력은 남긴 항목이었다.
- 55개는 확정 저장된 영상이 0바이트인 시도였다. 카드 개수와 완성된 방송 개수는 다르다.
- 별도로 구형 HLS 이력 4개도 남아 있었다.
- 오류 메시지 집계: 시간축 누락/불연속 12건, 저장 큐 적체 10건, SSD 병합 여유 공간 부족 7건, 영상·음성 트랙 변경 6건. 오래된 일반 중단 메시지만 남은 항목은 구체 원인을 새로 단정하지 않았다.
- 정상 앱 종료로 기록된 종료 사유도 20건 있었다. `interrupted` 또는 중단 관련 문구를 모두 동일한 수신 결함으로 해석하면 안 된다.
- 병합 실패 상태 17건(병합/검증 실패 9, 시간 초과 7, 대상 녹화 없음 1)도 별도로 남아 있었다. 녹화 중단과 병합 실패는 서로 다른 단계다.

### 파편화 이유

1. 원본 수신기는 시간축 불연속이나 트랙 변경을 감지하면 해당 녹화를 끝낸다. 같은 방송이 계속 켜져 있으면 자동녹화가 재시도하며 새 녹화 ID를 만든다.
2. `RecordingLibrary`는 현재 각 녹화 ID를 개별 카드로 표시한다. 방송 ID가 같다는 안내만 붙이고 하나의 방송 회차 카드로 접어서 묶지는 않는다.
3. 영상만 제거한 과거 이력과 빈 시작 실패도 유지되어, 오래된 문제와 오늘의 문제를 한 목록에서 보게 된다.

### 최근 SSD 중단의 구조적 원인

- 시작 전 SSD 선택은 여유 20 GiB 이상인지 확인한다.
- 수신 중에는 `10 GiB + 같은 SSD에 남은 모든 미병합 녹화의 원본 용량 + 다음 조각 여유`를 요구한다.
- 삭제 직전 미완료 SSD 보관 이동 12건, 원본 약 65.61 GiB가 남아 있었다. 이때 필요한 병합 여유 공간은 약 75.61 GiB 이상이다.
- 실제 실행 로그에 SSD 여유 75 GiB에서 선택된 직후 `BROWSER_CAPTURE_DISK_FULL`로 녹화 시작이 거부된 사례가 있었다. SSD가 물리적으로 0바이트까지 찬 것이 아니라 예약 공간 조건에 걸린 것이다.
- 자동녹화는 실패 후 지연 재시도한다. 공간 조건이 해결되지 않은 채 시작 검사를 통과하고 수신 검사에서 다시 실패하면 짧은/빈 기록이 더 쌓인다.
- SSD → HDD 이동은 병합과 원본 조각 정리가 끝난 뒤에만 가능하다. 따라서 병합 대기나 실패가 쌓이면 SSD 공간 예약도 함께 남는다.

초기화는 이 적체를 없애지만 위 설계를 수정하지는 않는다. 후속 개선 대상으로 시작/수신 공간 검사 통일, 공간 확보 확인 전 재시도 억제, 방송 회차 아래 재시도 이력 묶음, 시간축/트랙 변경 시 안전한 새 구간 전환을 권장한다. 이번 CHZZK 요청은 원인 검토와 데이터 초기화이므로 녹화 엔진은 임의로 변경하지 않았다.

## 초기화 범위

- HDD의 `D:\Astumi\CHZZK`와 SSD staging의 CHZZK 전용 하위 폴더: 영상, 조각, 채팅, 녹화 메타데이터, 병합/이동 증빙.
- 앱 데이터 `streaming`: 현재/구형 녹화 목록, 시작 캐시, 다시보기 인덱스/캐시, 진단·정비 로그.
- CHZZK 채널 즐겨찾기 3개와, 사용자가 추가로 승인한 자동녹화 예약 3개.
- CHZZK 채널 프로필 캐시와 과거 녹화 진단용 임시 자료.
- 공용 개발 로그에서는 `atsumi_lib::streaming` 이벤트만 제거하며 히토미 이벤트는 유지한다.
- 네이버 로그인 프로필, 그리드 설정, 히토미 DB·앨범·즐겨찾기, 프로그램 소스와 플레이어 자산은 유지한다.
- 삭제는 휴지통 이동이 아닌 영구 삭제이며, 원시 로그나 영상 백업을 새로 만들지 않는다.

### 초기화 완료 확인

- HDD 녹화 전용 트리: 18,461개 파일, 510,571,626,311바이트 삭제.
- SSD 녹화 전용 트리: 6,646개 파일, 71,747,353,066바이트 삭제.
- 녹화 인덱스·재생 캐시·로그: 306개 파일, 45,869,683바이트 삭제.
- 이전 녹화 진단 사본: 6개 파일 삭제. CHZZK 즐겨찾기/예약/프로필 캐시 5개 파일 삭제.
- 현재 공용 로그에서 CHZZK 이벤트 82개, 과거 실행 로그 사본에서 7개만 제거했다. 다른 소스 이벤트는 유지했다.
- 모든 명시적 삭제 대상이 없어졌음을 확인했다. 총 크기는 약 542.37 GiB이며 파일 시스템 여유 공간 증가량과는 메타데이터/할당 단위 때문에 다를 수 있다.
- 히토미 공용 DB 본체와 WAL의 SHA-256이 삭제 전후 동일했다. 네이버 로그인 프로필은 유지했다.
