# CHZZK 재생 지연 조사

현재 공식 플레이어의 UI·마도 모드 구현 및 중복 수신 없는 배속 녹화 후속안은 [최신 시청 확장 명세](CHZZK_PLAYER_EVOLUTION.md)를 함께 참고한다.

최초 조사일: 2026-09-10. 공유 작업공간 `2849` 기준. 아래 2026-09-11 보충을 제외한 기존 조사는 **별도 HLS 수신·녹화 경로**에 관한 것이며, 이후 추가된 공식 페이지 시청·화면 녹화 경로와 구분해야 한다. 이 문서는 개선안이며 실측 재생 성능을 보증하지 않는다.

## 2026-09-11 보충: 배속 따라잡기와 녹화의 분리

현재 공식 시청은 CHZZK의 원래 플레이어가 영상을 받는다. Atsumi가 저장한 15초 조각을 다시 읽어 라이브 화면을 보여주는 구조가 아니다. 15초는 복구 가능한 녹화 파일을 확정하는 단위이지, 공식 플레이어에 추가하는 재생 대기 시간이 아니다.

다만 공식 화면 녹화는 `browser_capture.js`에서 해당 `video.captureStream()`을 `MediaRecorder`로 기록한다. **시청과 녹화가 같은 재생 영상에 묶여 있다.** 녹화 시작은 1배속·비탐색 상태에서만 허용하고, 녹화 중 배속 변경·탐색은 마지막 조각을 마무리한 뒤 중단 사유를 남긴다. 이번 UI 수정에서 이 보호 조건은 제거하지 않았다.

- [Cheese Plus 소스](https://github.com/kyechan99/chzzk-plus/blob/main/src/feature/bufferDisplay.ts)의 지연 표시는 `seekable` 끝과 재생 위치의 차이이며, 없으면 `buffered` 끝으로 대체한다. 이는 시청 가능한 최신 지점까지의 거리이지 송출자 화면부터 시청자 화면까지의 실제 지연 측정은 아니다. [프로젝트 설명](https://github.com/kyechan99/chzzk-plus)은 빨리감기를 제공하지만 녹화 기능은 제공하지 않는다고 밝힌다. 따라서 같은 조작으로 Atsumi의 녹화도 온전하다는 증거로 쓸 수 없다.
- [W3C Media Capture 초안](https://www.w3.org/TR/mediacapture-fromelement/#html-media-element-media-capture-extensions)은 재생 요소의 출력을 실시간으로 캡처하며 1배속이 아닌 음성은 시간 축을 늘이거나 줄이는 처리가 적용된다고 명시한다. 현재 방식에서 배속만 풀면 영상 진행 속도·녹화 길이·음성·채팅 시간 대응을 보존한다고 보장할 수 없다.

### 작은 범위에서 가능한 방식 — 제안, 아직 미구현

`실시간으로` 버튼으로 **녹화하지 않을 때만** 잠깐 1.1~1.2배 재생하고, 최신 지점과의 안전한 여유까지 접근하면 1배속으로 되돌린다. 공식 플레이어의 자체 보정·버퍼 부족·광고·다시보기/타임머신 상태를 고려해야 한다. 네트워크에 아직 도착하지 않은 장면까지 당길 수는 없다.

녹화 시작 요청과 따라잡기는 상호 배타적이어야 한다. 따라잡기를 해제하고 같은 영상이 정상 1배속으로 안정된 것을 확인한 다음, 새 녹화를 시작한다. 진행 중 녹화를 몰래 중단·재시작하거나 빠진 구간을 정상 녹화로 표시하지 않는다. 배속·화질 변경 때 실제 저장 파일 길이/음성/채팅 대응을 합성 입력으로 검증해야 한다.

### 녹화 중에도 독립적으로 따라잡는 방식 — 별도 설계 필요

원본 영상 데이터를 한 번 수신한 후 **시간 정보가 유지된 저장 경로**와 **자유롭게 배속/탐색하는 재생 경로**로 나누는 것이 적합하다. 현재 공식 플레이어의 화면 캡처에 배속 옵션만 덧붙이는 규모는 아니다. 공식 재생이 실제 사용하는 전송 경로에서 인코딩된 데이터를 안전하게 공유할 수 있는지부터 검증해야 한다. 별도 HLS 수신기를 동시에 켜면 중복 트래픽이 발생하므로, 이를 ‘공유 수신’으로 부르지 않는다. 암호화된 미디어나 접근 제한을 우회하는 설계는 포함하지 않는다.

수용 기준은 재생속도/탐색을 바꿔도 저장한 구간 순서·시간·음성이 원본과 같고, 채팅의 방송 시각/녹화 시각 대응이 유지되며, 재생과 저장이 동일 구간을 두 번 내려받지 않는 것이다. 앱 중단 시 복구와 원본 화질 전환도 함께 검증해야 한다.

## 결론

현재 지연의 주된 개선 지점은 그리드 프로그램 설치가 아니라 **일반 HLS 전체 조각을 받아 저장한 다음 재생하는 수신 경로**다. 제공된 채널의 공개 API와 재생목록을 확인한 결과, 일반 `HLS`와 별도로 `LLHLS`도 실제 제공되고 있다. Atsumi는 현재 일반 `HLS`만 선택하며, LL-HLS의 부분 조각을 명시적으로 거부한다.

다음 단계로 권하는 작업은 **LLHLS 부분 조각을 한 번 수신해 로컬 재생과 녹화가 공유하도록 확장하는 것**이다. 공식 웹보다 약 1초 이내로 늦는 것을 검증 목표로 삼을 수 있지만, 현재 원본의 `PART-HOLD-BACK`이 약 3.051초이므로 방송 발생부터 화면 표시까지 총 1초를 약속할 근거는 없다.

## 확인 범위와 실제 관측값

사용자가 제공한 채널 `b3e262a2795f17734c149afc738ad250`에 대해 익명 공개 API와 그 API가 반환한 master/media 재생목록 텍스트만 읽었다. 영상·오디오·초기화 조각을 요청하지 않았고, 쿠키를 사용하지 않았으며, 서명 주소나 토큰을 출력하거나 파일로 저장하지 않았다. 앱을 실행하거나 녹화를 시작하지 않았다.

- `live-detail`: 방송 상태 `OPEN`, `timeMachineActive=true`, `HLS`와 `LLHLS`를 모두 광고한다. 두 항목의 `protocol`은 모두 `HLS`이고 `mediaId`로 구분된다.
- Atsumi가 time-machine 방송에서 사용하는 공개 `live-playback-json` fallback도 두 항목을 모두 제공했다.
- 아래 수치는 fallback에서 최고 해상도로 광고한 **1080p** 변형의 관측값이다. master에는 5개 변형이 있었다.
- 관측 시각: **2026-09-10 23:44:08 KST** / `2026-09-10T14:44:08Z`.

| 재생목록 항목 | 일반 HLS | LLHLS |
| --- | --- | --- |
| `EXT-X-TARGETDURATION` | 10초 | 10초 |
| 관측된 전체 조각 길이 | 약 4.166667~4.167초 | 약 4.166667~4.167초 |
| 전체 조각 개수 | 8 | 8 |
| 부분 조각 개수 | 0 | 21 |
| 관측된 부분 조각 길이 | 없음 | 1.017, 1.0, 0.15, 0.167, 0.166667초 |

이는 한 채널의 한 시점 표본이다. 모든 방송·화질에서 같은 값이 유지된다는 의미는 아니다. 메타데이터를 관측했을 뿐 공식 웹과 Atsumi의 화면 차이, 조각 다운로드 시간, 디스크 처리 시간은 측정하지 않았다.

## 현재 코드에서 생기는 지연

다음 위치는 조사 시점의 줄 번호이며 이후 UI 수정으로 이동할 수 있다.

| 단계 | 현재 동작과 근거 | 이번 표본에 대입한 의미 |
| --- | --- | --- |
| 원본 선택 | [provider.rs](../src-tauri/src/streaming/provider.rs), 91~107행의 fallback 이후 118~138행에서 `protocol=HLS`, `mediaId=HLS`만 선택 | 공개 LLHLS 항목을 사용하지 않음 |
| HLS 해석 | [hls.rs](../src-tauri/src/streaming/hls.rs), 107~113행에서 `PART`, `PRELOAD-HINT`, `SKIP`, byte-range 거부 | 플레이어 옵션만 바꿔도 부분 조각은 도착하지 않음 |

| 재생 목표 | [StreamingPlayer.tsx](../src/features/streaming/StreamingPlayer.tsx), 조사 시점 57행은 `lowLatencyMode=false`, `liveSyncDurationCount=2`, `liveMaxLatencyDurationCount=5` | 설정상 목표는 **20초**, 강제 추격 기준은 **50초**. 실제 화면 지연 실측값은 아님 |
| 실시간 버튼 | 같은 파일 조사 시점 94~99행에서 `hls.liveSyncPosition`으로 이동 | 위의 안전 지연을 포함한 지점으로 이동하므로 방송 원본의 가장 최신 프레임을 뜻하지 않음 |

`maxBufferLength=20`은 재생 전에 반드시 20초를 채우는 대기 시간이 아니다. 앞쪽 버퍼를 얼마나 확보하려 하는지에 관한 값이다. 이 사안에서 직접적인 지연 설정은 live-sync 관련 값이다. [hls.js API 설명](https://github.com/video-dev/hls.js/blob/v1.7.2/docs/API.md#livesyncdurationcount)

설치된 hls.js는 `1.7.2`다. 그 버전은 명시한 `liveSyncDurationCount × targetduration`을 목표로 사용하고, 일반 HLS에서 `liveSyncPosition`을 최소 한 target duration만큼 목록 끝 뒤에 두도록 제한한다. 따라서 target이 10초인 이 목록에 `liveSyncDuration=1`만 지정해도 1초 위치로 이동하지 않는다. stall 발생 시 목표가 증가할 수 있고 현재 옵션으로는 속도를 올려 따라잡는 기능도 동작하지 않는다. [hls.js 1.7.2 latency controller](https://github.com/video-dev/hls.js/blob/v1.7.2/src/controller/latency-controller.ts)

플레이어가 읽는 로컬 목록도 별도 갱신 주기를 갖는다. hls.js는 이 표본처럼 최신 실제 조각 길이가 target보다 짧고 재생 위치가 충분히 가까우면 약 4.167초를 사용하며, 목록이 바뀌지 않았으면 target의 절반인 5초를 사용한다. 따라서 수신 측 갱신과 플레이어 측 갱신의 위상 차이도 영향을 준다. 다만 이를 위의 20초 목표에 무조건 단순 합산하면 중복 계산할 수 있다. [hls.js 1.7.2 reload 계산](https://github.com/video-dev/hls.js/blob/v1.7.2/src/utils/level-helper.ts)

## 1초라는 목표의 구분

1. **공식 웹 대비 추가 지연**: 같은 방송·같은 화질의 같은 장면이 공식 웹에 표시된 시점과 Atsumi에 표시된 시점의 차이다. 원본 인코딩 지연은 대부분 공통으로 포함되므로, Atsumi의 LLHLS 경로가 개선되면 약 1초 이내 차이를 검증 목표로 삼을 수 있다. 아직 달성 여부를 측정하지 않았다.
2. **방송 발생부터 표시까지의 총 지연**: 송출자의 캡처·인코딩·업로드·서버 처리·원본 게시·전송·플레이어 지연을 모두 포함한다. 이번 표본의 서버 권장 안전 거리는 3.051초다. 이를 따르는 재생의 총 지연이 1초라고 보장할 수 없다.
3. **플레이어가 표시하는 live-edge 거리**: hls.js가 추정하는 목록 끝과 현재 재생 위치의 차이다. 로컬 목록이 원본보다 늦게 갱신될 수 있으므로 이 숫자만으로 위 두 수치를 대신할 수 없다.

일반 HLS에서는 약 4.167초짜리 전체 조각이 게시될 때까지 기다리는 구조적 제약이 있다. LLHLS에서는 약 1초 부분 조각을 먼저 받을 수 있지만, `PART-HOLD-BACK=3.051`은 유지하는 것이 기본이다. 이 값은 물리적인 절대 하한을 실측한 결과가 아니라 서버가 권장하는 재생 안전 거리다. Apple의 재생목록 작성 지침도 part target의 세 배 이상을 요구한다. [Apple HLS authoring specification](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices/)

따라서 현재 코드의 20초 목표와 5초 수신 대기는 5~15초 이상의 체감 차이를 설명하는 강한 원인 후보다. 하지만 공식 웹 재생과 비교하지 않은 상태에서 정확히 몇 초가 어느 단계에서 발생했다고 확정하지 않는다.

## 그리드 설치의 의미

네이버 공식 안내는 Chrome·Edge·웨일의 고화질 웹 시청에 라이브 스트리밍 커넥터와 브라우저 확장이 필요하며, 이 연결의 문제를 별도로 다룬다. 이는 공식 웹의 지원 경로에 관한 안내다. [네이버 고화질 라이브 시청/그리드 안내](https://help.naver.com/service/23946/contents/23231?lang=ko&osType=COMMONOS)

Atsumi의 현재 수신기는 Rust HTTP 요청으로 공개 CDN 재생목록을 읽는다. 브라우저 확장, 설치된 NLiveConnector 또는 P2P SDK를 호출하는 경로가 없다. 따라서 **PC에 그리드를 설치하는 것만으로 Atsumi의 HLS 선택·5초 대기·20초 목표가 바뀌지는 않는다**. 이번 익명 요청에서 LLHLS 목록을 읽을 수 있었으므로, 저지연 지원의 첫 구현 단계에 그리드 연동이 필요하다는 근거도 없다. 이것은 현재 코드와 관측값에 따른 판단이며 향후 서비스 정책·접근 조건까지 보장하는 것은 아니다.

Streamlink의 현재 CHZZK 구현도 `mediaId=HLS`를 선택한다. Streamlink로 교체한다는 사실만으로 LLHLS 지원이나 공식 웹 수준 지연이 자동 확보되지는 않는다. [Streamlink CHZZK 소스](https://github.com/streamlink/streamlink/blob/master/src/streamlink/plugins/chzzk.py)

## 권장 구현 순서

### 1. 원인별 계측과 제한적인 일반 HLS 개선

수신 목록 요청·새 조각 발견·수신 완료·저장 완료·로컬 게시·화면 재생 시점을 구분한다. 원본 `PROGRAM-DATE-TIME`, hls.js `playingDate`, 로컬 목록 나이와 재생 버퍼를 함께 기록하되 서명 URL과 토큰은 남기지 않는다. 화면 비교가 없는 값은 총 지연으로 표시하지 않는다.

일반 HLS를 유지하는 동안에는 다운로드 처리 후 무조건 긴 대기를 추가하는 방식과 과도한 live-sync 여유를 검토할 수 있다. 원본이 허용하는 갱신 규칙·요청량을 지키며 갱신 시점을 맞추고, 작은 live-sync 목표를 안정성 실험으로 검증한다. 반복적인 초당 다회 polling이나 관측된 짧은 조각만 보고 `TARGETDURATION`을 임의로 낮추는 방법은 채택하지 않는다. 향후 긴 조각과 목록 규칙을 깨뜨릴 수 있다. 이 단계만으로 안정적인 1초 지연을 해결했다고 주장하지 않는다.

### 2. LLHLS를 수신기의 정식 경로로 추가

공개 API가 실제 광고한 `mediaId=LLHLS`를 선택하고, 없으면 일반 HLS를 사용한다. 임의 CDN 주소·화질 URL 재작성 없이 기존 출처 검증과 인증 정보 전달 범위를 유지한다.

파서는 part 순서·독립적으로 디코딩 가능한 시작점·초기화 맵·불연속 구간·gap·preload hint·server control을 해석해야 한다. `CAN-BLOCK-RELOAD`에 따라 `_HLS_msn`과 `_HLS_part`를 사용해 새 부분 조각을 기다리고, delta update를 실제 지원하기 전에는 `_HLS_skip`을 요청하지 않는다. preload hint는 취소·변경될 수 있으므로 확정된 part와 동일한 것으로 섣불리 기록하지 않는다. 이러한 기능이 LL-HLS가 전체 조각 게시 전 미디어를 전달하고 polling 지연을 줄이는 방식이다. [Apple LL-HLS 설명](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls?changes=_7&language=objc)

### 3. 한 번 수신한 부분 조각을 재생과 저장이 공유

원격 미디어 수신자는 백엔드 하나로 유지한다. 수신한 완전한 part를 검증해 공용 로컬 저장소에 넣고, 플레이어는 그 part를 곧바로 소비한다. 동일 바이트는 순서대로 녹화 segment 구성에도 사용한다. 원격 URL을 플레이어에 직접 넘겨 두 번째 수신 경로를 만들지 않는다.

- 중복 방지 키는 방송/표현 식별자, discontinuity sequence, media sequence, part index와 map 식별 정보를 고려한다. 재요청·중복 목록·토큰 갱신이 바이트 중복 저장으로 이어지면 안 된다.
- 모든 part를 확보한 부모 segment는 로컬에서 조립한다. 같은 구간의 전체 segment를 녹화용으로 다시 다운로드하지 않는다. fMP4 조립의 map, 시각 정보와 container 유효성을 검증한다.
- 첫 접속에서는 과거 완료 segment를 선택해 받을 수 있다. 그 뒤에는 part가 시작되는 경계를 명확히 정해 겹치는 구간을 이중 수신하지 않는다.
- part와 journal이 복구 가능한 상태가 된 뒤 게시하는 방식을 우선 검토한다. 녹화의 전체 segment 확정은 부모 구간의 완성을 기다릴 수 있지만 화면이 그 완성까지 기다려서는 안 된다. part별 동기화가 저장장치에 주는 비용은 실제 측정한다.
- 아직 확정하지 않은 마지막 부모 segment의 part도 journal에서 복구하도록 설계한다. 메모리에만 게시하는 방식을 선택한다면 강제 종료 시 이미 본 마지막 구간이 저장되지 않을 수 있다는 의미가 달라지므로, 현재 복구 보장과 별도로 명확히 정의해야 한다.
- 메모리와 임시 part 개수에 상한을 두고 디스크 지연·가득 참·플레이어 분리 시 동작을 정한다. 녹화 실패를 재생 성공으로 감추지 않는다.

이 방향은 현재의 한 번 수신 원칙을 보존할 수 있지만, 현 구현에 옵션 하나를 추가하는 규모는 아니다. 현재 [protocol.rs](../src-tauri/src/streaming/protocol.rs)의 24~25행은 모든 query를 거부하고 동기적으로 완료된 파일을 반환한다. LL-HLS 로컬 목록의 blocking reload와 제한된 delivery directive를 구현하거나, part 갱신 통지를 받는 로컬 loader를 만들어야 한다. 어느 방식이든 세션 토큰·출처·경로 검증과 요청 취소를 유지해야 한다. live view와 archive view는 같은 바이트를 공유하면서 서로 다른 진행 상태를 보여줄 수 있어야 한다.

### 4. 재생 추격·되감기·fallback 의미 정의

로컬 목록이 part를 공급할 때 `lowLatencyMode=true`를 사용하고 원본 `PART-HOLD-BACK`을 기본값으로 삼는다. `liveSyncDurationCount=2`를 그대로 남겨 part hold-back을 다시 전체 target의 두 배로 덮어쓰지 않는다. 허용된 좁은 범위의 재생속도 보정은 buffer가 충분할 때만 사용한다.

사용자가 과거로 이동하면 자동 추격을 멈추고, “실시간으로”를 눌렀을 때만 현재 안전한 LLHLS 위치로 돌아간다. 비활성 화면·프라이버시 모드로 플레이어가 종료되어도 수신·녹화의 연속성은 유지한다.

LLHLS 목록이 없어지거나 part 지원 조건이 달라지면 일반 HLS fallback을 명시적으로 표시한다. 이미 수신한 부모 구간과 fallback 시작점을 맞추고, 누락된 part를 복원할 수 없다면 누락을 표시한다. parts 일부를 받은 뒤 부모 전체를 다시 받아 메우는 선택은 일부 바이트를 중복 수신하므로 엄밀한 한 번 수신 원칙의 예외다. 기본 동작은 이를 조용히 수행하지 않고, 중복 없이 복구할 수 없을 때 gap을 알리는 것으로 정한다. 암호화나 권한 제한은 fallback으로 우회하지 않는다.

## 구현 후 검증과 수용 기준

이번 조사는 문서와 메타데이터만 다뤘으므로 아래 항목은 아직 실행하지 않았다.

1. 가짜 upstream으로 10초 target/약 4.167초 segment/약 1초 part 표본을 재현한다. 부분 조각이 부모 segment 완료 전에 화면 공급 경로로 나오는지 검증한다.
2. 실제 미디어 요청을 계수해 동일 part의 재생·저장 이중 수신과 part/부모 전체 중복 수신이 없는지 확인한다. 오류 재시도는 별도 계수하고 원인을 남긴다.
3. 중복·누락·순서 변경·맵 교체·불연속·짧은 마지막 part·취소된 preload·재연결·LLHLS→HLS 전환을 검증한다. 강제 종료 후 확정된 바이트와 archive 길이·순서·gap이 일치해야 한다.
4. 정상 조건과 네트워크/디스크 지연 조건에서 동시 시청·녹화, 되감기와 복귀, 화면 비활성화, 종료·업데이트 보호를 검증한다. 저지연을 위해 녹화 완전성과 종료 보호가 약화되어서는 안 된다.
5. 사용자 승인된 재생 비교에서 같은 채널·화질의 공식 웹과 동시 관측하고 startup, 지속 재생, stall 이후 차이를 나눠 보고한다. **공식 웹 대비 추가 지연 중앙값 1초 이내**를 우선 목표로 두되 상위 지연값과 재버퍼링 횟수도 함께 제시한다. 두 플레이어가 같은 장면을 표시한 시간을 비교해야 하며 hls.js의 local-edge 숫자만으로 통과 처리하지 않는다.
6. 총 지연을 평가하려면 송출 시각이 알려진 영상 또는 별도의 기준 시각이 필요하다. 원본 시각 기준과 시계 오차가 검증되지 않은 `PROGRAM-DATE-TIME`만으로 방송 발생부터 표시까지의 총 지연을 단정하지 않는다.

현재 근거로 확정할 수 있는 것은 **이 채널에 공개 LLHLS 경로가 있고, 현재 Atsumi가 그 경로를 사용하지 않으며, 큰 target 기반 대기가 발생하도록 설정되어 있다는 것**이다. 다음 구현의 우선순위는 그리드 설치 안내보다 LLHLS 수신·로컬 part 공유·복구 가능한 녹화 확장이다.
