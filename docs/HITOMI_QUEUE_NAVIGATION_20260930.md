# Hitomi 작업 큐·탐색 복원 개선 (2026-09-30)

적용 위치: 공유 개발 워크스페이스 `2849`. 기존 파일·DB·오류 이력을 삭제하지 않고 UI와 관측 경로를 개선한다. 릴리즈, Git 커밋·푸시, PC 종료는 이번 작업 범위가 아니다.

## 요청별 반영

| 요청 | 반영 내용 |
| --- | --- |
| 1. 큐 시각화·취소 | 활동 기록 → **다운로드 큐**. 요청 묶음/전체 큐, 100개씩 페이지 이동, 선택·요청 전체·해당 요청 이후 취소. |
| 2. 멈춘 UI 밖에서 관측·개입 | 인증된 로컬 제어 경로와 `tools/atsumi_control.ps1`. 상태·큐 조회, UI만 복구 요청, 명시한 항목 취소. |
| 3. 상세·연관 앨범 상태 | Explore·상세·연관 앨범에 공통 상태 아이콘과 색상. 상태 이름은 툴팁·접근성 이름으로 제공하고 완료 글자를 중복 표시하지 않는다. |
| 4. 수신 여부 가독성 | 완료는 초록 카드와 더 진한 표지 덮개, 검토는 주황, 해시·검증은 보라, 실행은 청록, 실패는 붉은 테두리. Explore와 관련 갤러리에 동일하게 적용하며 완료 표지는 hover/focus에서 선명해진다. |
| 5. Ctrl+클릭 | 후속 요청에 따라 앨범 카드 Ctrl+클릭은 다중 선택으로 복원. 작가·태그·검색 제안·큐 항목·관련 갤러리는 배경 열기를 유지. 2개 이상 선택 시 Enter는 모두 개별 상세 탭에 열고 Ctrl+Enter는 다운로드. |
| 6. 진행 표시·ETA | 활동 아이콘 원형 진행률, 요청별 분할 막대·단계별 건수·전체 큐 예상 종료. 아래에 10개 아이디어 정리. |
| 7. ESC | 모달/활동 패널/검색 제안 → 보이는 상세 → 현재 검색 순서. 최소화된 상세 탭을 몰래 닫지 않는다. |
| 8. Alt-Tab 이후 이동 | 최상단 상세로 포커스를 되돌리고 A/D·방향키를 처리. 입력창·모달·활동 패널은 우선권 유지. |
| 9. 미리보기 선로딩 | 확대해 보는 미수신 앨범 페이지 앞뒤 각각 2장. 양면 보기라면 펼친 두 장의 바깥쪽 각각 2장. |
| 10. 닫기 확인 | 개별 X는 즉시 닫는다. 상세 탭이 여러 개일 때 최우측 전체 닫기 X에만 확인창. ESC는 한 단계 복귀로 유지하고 실행 취소 가능. |
| 11. 부모 화면 복귀 | 앨범 A → 작가 검색 → 앨범 B에서 B를 닫으면 검색으로, 검색을 닫으면 A로 복귀. 검색 페이지·스크롤과 상세 미리보기 묶음·스크롤을 기억. |
| 12. 닫기 실행 취소 | Ctrl+Z로 가장 최근 닫기 또는 기존 제외·격리 작업 취소. Ctrl+Shift+T는 닫은 화면 복원 전용. 입력 중 Ctrl+Z는 편집기의 기존 동작 유지. |

## 취소와 진행률의 기준

- 대기/정보 확인/다운로드/해시/검증/재시도 대기만 실제 실행 큐에 포함한다. 검토 필요·실패·중단은 자동 완료로 바꾸지 않는다.
- 큐 취소는 기존 트랜잭션·리비전 검증을 사용하는 정상 취소 API를 200개씩 순차 호출한다. 이미 완료된 항목은 건너뛰며, 파일·manifest·오류 이력을 지우지 않는다.
- 확인창을 준비할 때 대상 entry ID를 고정한다. 그 이후에 추가된 작업을 함께 취소하지 않는다. 확인용 스냅샷은 한 읽기 트랜잭션이며 최대 10,000건이다.
- 나중 요청이 이미 있던 작업을 재사용한 경우 최초 등록 요청 소유로 남긴다. **‘이 요청 이후 취소’가 그 이전의 작업까지 취소하지 않도록** 한 기준이다.
- 요청 선택기는 활성 요청을 우선한 최근 100묶음을 제공한다. 전체 큐는 별도로 페이지 끝까지 볼 수 있다. 실시간 활동 기록의 최근 50건 제한과 다르다.
- 완료 %의 분자는 실제 `completed`만이다. 검토·실패·취소·격리는 따로 표시하며, 일이 멈췄다고 성공률 100%로 만들지 않는다.
- ETA는 최근 30분의 정상 완료 속도로 계산한 **전체 실행 큐의 거친 추정**이다. 최근 완료가 3건 미만, 관측 구간이 1분 미만, 5분 이상 정상 완료가 없으면 계산을 보류한다. 페이지 수·네트워크 재시도·검토·병합 작업에 따라 실제 시각이 달라진다. 다른 소스의 녹화 등 모든 PC 작업의 종료 시각이 아니다.

## UI가 멈췄을 때

PowerShell에서 공유 워크스페이스를 기준으로 실행한다.

```powershell
# 즉시 상태 / 큐 확인 (읽기 전용)
.\tools\atsumi_control.ps1 -Action Status
.\tools\atsumi_control.ps1 -Action Queue

# 기본 5초 간격으로 12번 관측. 더 필요하면 Samples를 명시한다.
.\tools\atsumi_control.ps1 -Action Watch -IntervalSeconds 5 -Samples 12

# UI만 다시 불러오기. 다운로드 프로세스를 종료하지 않는다.
.\tools\atsumi_control.ps1 -Action Recover -ConfirmAction

# Queue 결과의 정확한 entryId를 확인한 뒤 필요한 경우에만 실행
.\tools\atsumi_control.ps1 -Action Cancel -EntryIds '확인한-entryId' -ConfirmAction
```

`Status`에는 UI 마지막 응답으로부터 경과한 시간, renderer epoch, 메모리, 응답 없음 여부, 복구 대기, 마지막 화면 저장 시각이 나온다. Queue는 SQLite 읽기 전용 연결을 사용하며 UI의 IPC 응답을 기다리지 않는다. 외부 Queue 조회는 100개씩 `-Page 2`, `-IncludeSettled`를 사용할 수 있다.

서버는 `127.0.0.1`의 임시 포트만 사용한다. 앱 실행마다 새 토큰을 발급하고 Host·토큰을 검증하며 브라우저 Origin 요청을 거부한다. 토큰은 앱 데이터의 `diagnostics/control-endpoint.json`에만 두고 화면/일반 로그에 출력하지 않는다. 임의 명령 실행, 임의 파일 접근·삭제, 강제 종료 API는 없다. 명시적 변경 요청은 현재 UI epoch도 요구한다.

UI 복구 API의 ‘접수’는 복구 성공이 아니다. 이후 새 epoch와 최근 응답을 확인해야 한다. UI 문서/renderer 문제는 이 경로로 복구를 요청할 수 있지만 네이티브 메인 루프·운영체제·저장장치 자체가 멈춘 경우까지 강제로 복구하지 않는다. 원래 프로세스의 메모리에 외부에서 임의 상태를 덮어쓰지 않는다.

탐색·상세 상태는 **변경된 경우에만 최대 2초 간격**으로 저장한다. 검색 탭 순서·페이지·스크롤, 열린 상세 순서·최소화 상태·출발 화면·미리보기 위치를 복원한다. 이미지 바이트·큐 본문은 복제하지 않는다. 저장 직후 2초 이내의 마지막 조작은 복원되지 않을 수 있다. 복원 체크포인트는 128KiB, 검색/상세 각각 64탭, 최근 위치 96개, 유효기간 24시간으로 제한한다. 실행 취소 목록은 현재 UI 세션의 최근 24회 닫기를 기억한다.

## 성능·새로고침

`download:changed` 자체는 완료마다 전체 다운로드 목록을 재요청하지 않는다. 진행률은 ID별 저장소로 100ms 묶어서 반영하고, 상태 변경 시 해당 앨범의 데이터가 바뀐다. 그러나 후속 조사에서 **자동 중복분류 완료 경로도 `downloadsRefresh`를 올려 전체 목록을 다시 읽는 것**을 확인했다. 이벤트 누락 복구(`download:resync`)와 명시적 변경·새로고침도 같은 경로를 사용한다. `downloadLibraryPageList`는 200개씩 끝까지 조회하고 각 페이지마다 목록을 반영한다.

별개로 상태 변경은 정렬/필터/작가 폴더를 재계산한다. `DownloadArtistFolderGrid`의 바깥 행 key가 그 행의 모든 작가 key를 합친 값이므로, 최신순 재배치로 행 구성원이 바뀌면 해당 행의 카드가 재마운트될 수 있다. 기존 썸네일 캐시가 있으므로 재마운트가 모두 이미지 재다운로드를 뜻하지는 않는다. 이는 코드 경로 확인이며, 앱이 종료된 이번 작업에서 실제 사용자 세션의 발생 빈도를 측정한 결과는 아니다.

새 큐는 전체 앨범 목록을 재로딩하지 않는 별도 SQL 조회이며 5초에 한 번, 동시에 하나만 조회한다. 변화가 없는 결과는 재렌더링하지 않는다. 화면 저장용 스크롤 이벤트는 250ms 묶고, 상세 탭 복원 시 메타데이터 조회는 최대 3개씩 진행한다. 추가 미리보기는 기존 중복 요청 합치기·캐시·우선순위·취소 규칙을 그대로 사용하고 확대 화면을 닫거나 이동하면 불필요한 구독을 해제한다. 무결성·중복 판정 기준, 다운로드 병렬도, 원본 검증은 완화하지 않았다.

### 후속 요청 6번: 해결안만 제시, 이번에는 미구현

1. 자동분류·병합·복원 응답에 영향을 받은 gallery ID와 revision을 포함하고 해당 앨범의 요약/목록 소속만 부분 반영한다. 제외·대표 판본 교체처럼 여러 앨범이 바뀌는 경우 관련 ID 모두를 반환해야 한다. ID가 불명확한 경우와 시작 시 초기 적재·명시적 새로고침·이벤트 누락 복구에는 전체 동기화를 남긴다.
2. 작가 카드의 부모 key를 행 구성원에 의존하지 않도록 바꾼다. 안정적인 작가 key를 가진 평면 grid 등을 검토하되 펼친 폴더·스크롤 위치·현재 선택은 보존한다.
3. 연속 구조 변경은 짧은 시간으로 묶고 영향을 받은 작가 그룹만 다시 계산한다. 최신순 정렬을 유지하며, 장기간 정렬을 고정하는 방식은 기존 요청과 충돌하므로 기본안에서 제외한다.
4. 전체/부분 목록 조회 횟수, 카드 mount 횟수, 실제 썸네일 요청 수를 따로 계측한다. 1건 완료 시 관련 없는 카드가 재마운트되거나 전체 페이지가 재조회되지 않는지 검증한다. 정상적인 썸네일 revision 무효화·캐시·취소 규칙은 유지한다.

## 후속 UI 정리 (요청 1~5)

- 활동 분류 탭은 헤더 바로 아래 같은 위치에 고정하고 본문만 스크롤한다. 기존 ‘기본 설명 1~2줄, 추가 정보는 툴팁·펼침’ 원칙에 따라 통계·오류 상세·취소 범위 설명을 접었다. 최근 50건·그룹별 최신순 정렬은 그대로다.
- 완료/대기/해시/검증/실패/중복 등은 하나의 상태 아이콘으로 표시한다. 선택 체크박스는 카드 좌측 상단 하나만 남겼다. 상태 아이콘은 우측이며 선택 체크박스와 역할이 다르다.
- 완료 표지만 색상 덮개로 낮은 대비를 만들고 hover/focus 시 원상 복귀한다. 검토 필요·실패는 가리지 않으며 더 강한 제외/격리 가림과 프라이버시 규칙도 유지한다. CSS 블러나 이미지 재가공은 추가하지 않는다.
- Ctrl+카드 클릭은 다중 선택, 여러 개 선택 후 Enter는 각 상세 탭 열기다. 첫 선택 앨범을 활성화하고 나머지는 배경에 열며 메타데이터 조회는 최대 3개로 제한한다. 입력창·버튼·IME 입력은 가로채지 않는다.
- 개별 X와 전체 X의 확인 정책을 분리했다. 전체 닫기를 취소하면 탭은 그대로 남으며 기존 닫기 실행 취소도 유지한다.

## 진행 상황 UI 아이디어 10개

1. **활동 아이콘 원형 진행률** — 조용하게 완료 비율 표시. 적용.
2. **요청별 분할 막대** — 완료/실행/검토/실패/취소를 색으로 분리. 적용.
3. **단계별 숫자 요약** — 대기·다운로드·해시·검증 건수를 구분. 적용.
4. **요청 묶음 선택기** — ‘이번에 요청한 것’과 누적 이력의 분모를 구분. 적용.
5. **예상 종료 시각 + 계산 보류 이유** — 근거가 없으면 숫자를 만들지 않음. 적용.
6. **하단 미니 작업 바** — 활성 건수와 ETA만 고정 표시. 아이콘/패널과 중복되므로 후보로 보류.
7. **요청 타임라인** — 작가 검색/요청 순서를 시간축으로 보고 잘못 추가한 구간 선택.
8. **단계 체류 시간 표시** — 오래 걸리는 앨범에 ‘해시 8분’처럼 병목 힌트 제공.
9. **최근 처리 속도·추정 범위** — ‘분당 2~4앨범, 14:20~14:40’처럼 불확실성을 시각화. 충분한 표본 축적 후 가능.
10. **완료/사용자 검토 알림 분리** — 정상 종료와 결정이 필요한 상태를 다른 안내로 표현. 단순 진행 때는 알림을 반복하지 않음.

## 단축키 검토 범위와 의도적으로 남긴 차이

Hitomi의 Explore·Downloads·Auto Find·상세·연관 앨범·검색 제안·새 큐의 탐색 동작을 통일했다. 이미지 비교 화면의 Ctrl 선택은 비교 대상 선택이며 ‘다른 화면 열기’가 아니므로 유지한다. Ctrl+Enter 다운로드, Ctrl+A 선택, Ctrl+Tab 주요 화면 전환도 그대로다. Danbooru의 단일 상세/이전 탐색 UI에는 별도 탭 모델이 없어 동일한 배경 탭 동작이 아직 없으며 이번 Hitomi 변경으로 임의 확장하지 않았다.

## 최초 작업 검증 결과

- 프런트엔드 전체: 131개 파일, **1,307개 테스트 통과**. 병렬 CPU 부하에 의한 시간 초과를 분리하기 위해 최종 전체 실행은 워커 4개로 제한했다. 마지막 큐 링크 수정 후 관련 74개 통합 테스트도 재통과했다.
- 백엔드 전체: **905개 통과, opt-in 등 26개 제외**. 이후 추가한 인증/Origin/헤더·본문 제한/큐 페이지/읽기 전용 검사를 포함해 관련 6개 테스트 재통과.
- TypeScript·프런트엔드 빌드·Rust 개발 실행 파일 빌드 통과. 기존 큰 JS 번들 경고는 남아 있다.
- 샘플 브라우저 화면에서 Ctrl+클릭 시 현재 검색 유지, 배경 상세 탭 추가, 다중 상세 X 확인창, 큐 패널 배치 및 동일 상태 배지를 확인했다. 실제 사용자 큐 취소·파일 삭제는 수행하지 않았다.
- 정상 개발 런처로 실제 앱 실행 성공. 외부 상태 응답 약 1초 이내의 UI pulse, 큐 조회와 완료 이력 2페이지(100개) 응답을 확인했다. 큐 조회 전체 PowerShell 호출 시간은 한 차례 측정에서 약 137ms였다(지속적인 성능 보장 수치는 아님).
- UI 복구 요청 후 **동일 앱 PID, 새 renderer epoch, 최근 pulse, 저장한 탐색 상태 동일**을 확인했다. 이 실행은 열린 검색/상세가 0개인 유휴 상태였다. 여러 탭·순서·부모 화면·스크롤 복원은 별도 단위/통합 테스트로 검증했으며 다운로드 중 의도적으로 프로세스를 고장 내는 시험은 하지 않았다.
- 개발 앱은 새 코드로 실행해 둔다. 기존 릴리즈 설치본 교체, 커밋·푸시, PC 종료는 수행하지 않았다.

## 후속 UI 정리 검증

- 프런트엔드 전체 1,323개 테스트 통과. 상태별 아이콘, per-ID 상태 반영/오래된 revision 무시, 관련 갤러리 가림, 선택 체크 중복 제거, 다중 Enter·Ctrl+Enter·IME, 개별/전체 닫기를 회귀 검증했다.
- TypeScript 검사와 프런트엔드 production 빌드 통과. 기존 500kB 이상 번들 경고는 남는다. 백엔드 코드는 이번 UI 정리에서 변경하지 않았다.
- 브라우저 샘플 앱에서 세 활동 탭의 버튼 x/y/너비가 동일함을 측정했다. Ctrl 다중선택 후 Enter로 두 탭을 열고, 전체 X 확인 취소 후 개별 X가 즉시 닫히는 것을 확인했다.
- 별도 샘플 화면에서 실제 카드·공통 상태 컴포넌트의 Explore/관련 갤러리 배경색·테두리색·덮개 투명도가 같은지 확인했다. 기존 CSS가 선 아이콘을 가리던 상속 문제도 시각 검증 중 발견해 수정했다.
- 실제 다운로드·파일·DB는 변경하지 않았고 네이티브 앱은 실행하지 않았다. 검증용 브라우저와 프런트엔드 서버만 사용했다. 릴리즈 설치본 교체·커밋·푸시는 하지 않았다.
