# Atsumi Ink — 요구와 결정 이력

작성일: 2026-09-23 · 연결 문서: [디자인 시스템 v0.1](ATSUMI_INK_V0_1.md)

## 읽는 방법과 한계

‘당시 설명’은 사용자에게 표시된 응답에 나온 근거를 요약한다. ‘해석’은 이번 명세를 만들며 도출한 제품 원칙이다. 확인하지 못한 내부 판단 과정은 재구성하지 않는다. 과거 제안은 사용자의 승인이나 후속 구현 근거가 없으면 확정 요구로 승격하지 않는다.

현재 대화의 사용자 메시지는 직접 확인했다. 다른 프로젝트 대화는 제목·요약으로 대상 선정 후 실제 userMessage와 공개 답변을 읽었다. 오래된 호출/진단 명령은 현재 작업 지시로 실행하지 않았다. 임시 이미지의 경로·사용자 DB의 상세 내역·전체 원문 대화 덤프는 이 문서에 복제하지 않는다.

## E01. 전체 탐색을 잃지 않는 분기 탐색

- **상황·요구(T0):** 전체 Explore → 좋은 앨범 → 해당 작가 검색 → 다운로드 → 원래 탐색 복귀 흐름에서 중단 지점을 다시 찾는 것이 불편했다. 이미 로드한 항목도 유지하기 원했고, 당시 RAM 500MB~1GB 사용을 허용했다.
- **당시 설명/대응:** 탐색 컨텍스트와 페이지 캐시·스크롤을 별도 보존하는 방향으로 진행했다.
- **이번 해석:** 목적은 무제한 캐시가 아니라 재탐색 비용 제거다. 검색을 더 여는 행위가 기존 탐색을 초기화하면 안 된다.
- **근거 코드:** `src/state/explorePageSession.ts`, `src/components/ExploreContextBar.tsx`, `src/features/hitomi/HitomiFeature.tsx`.
- **한계:** RAM 허용치를 현재 전체 영상 앱의 상한으로 간주하지 않는다. 디스크 지속성은 별도 요구다.

## E02. 로고의 검은 톤과 후순위 테마

- **요구(T0):** UI가 단조롭다는 문제 제기 → 테마 색과 명세 제안 → ‘로고의 검은톤 색상을 사용하는건?’ → 미리보기 확인 후 긍정. 밝은/다크/시스템 설정도 요청했지만 후순위로 지정했다.
- **이번 확인:** `src/atsumi-ink.css`에 Ink 표면, 로즈 강조, 틸 정보색과 상태색이 정의돼 있다.
- **이번 해석:** 검은 톤은 콘텐츠와 충돌하지 않는 바탕이다. 모든 요소를 동일한 회색으로 만드는 요구는 아니다.
- **경계:** 개별 HEX·로즈 강조·타이포 수치는 코드의 현행 선택이지 사용자 직접 지정값이 아니다. 미리보기 이미지가 보여주지 않은 동작까지 승인된 것으로 간주하지 않는다.

## E03. 요약 모드는 작은 이미지 모드가 아니다

- **요구(T0):** 태그 등 정보를 줄이고 미리보기 크기는 유지하면서 한 화면에 더 많은 앨범을 담고 싶다고 했다. 이후 즐겨찾기 태그는 공간이 충분할 때만 추가하기로 했다.
- **판단 배경:** 원하는 것은 이미지 판단의 효율이지 카드 수 자체의 최대화가 아니다.
- **명세 반영:** 상세/요약의 정보량을 분리하고, 태그 때문에 이미지를 줄이거나 카드를 억지로 늘리지 않는다.

## E04. 긴 설정 설명과 이질적인 드롭다운

- **요구(T0):** ‘바로 보이는건 2줄 내외여야하고(가능하면 1줄)’, 추가 설명은 마우스 호버로 제공. Auto Find 기준 드롭다운도 주변과 맞추길 요청했다.
- **보강(T3, 2026-09-02):** Danbooru 드롭다운도 주변 UI와 상이하다고 지적. 턴 `01a05e8c-bfd8-7702-919b-88fdf7763ba1`.
- **이번 해석:** 설명 자체를 삭제하라는 뜻이 아니라, 기본 정보와 보충 정보를 분리하라는 요구다. 키보드 포커스로도 도움말을 제공하는 것은 접근성 보완 제안이다.
- **현행 연결:** `DropdownSelect.tsx`, `SettingsDialog.tsx`. 모든 설명이 이미 2줄로 검증됐다는 뜻은 아니다.

## E05. 상세창의 조작 연속성

- **요구(T0):** Q/E 상세 탭 이동, A/D 추가 미리보기 묶음과 PAGE PREVIEW 이동, 숫자 직접 입력, 완료 앨범 원본 로드·크기 조절·체크 표시.
- **후속 문제:** 플로팅 앞에 있어도 직접 클릭해야 A/D가 작동했다. Related의 Ctrl+클릭은 포커스를 빼앗지 않는 새 탭이어야 했고, 다운로드 완료 여부도 표시하기 원했다.
- **이번 해석:** 포커스는 DOM에서 마지막 클릭한 곳이 아니라 현재 사용 맥락에 맞게 설계해야 한다. 다만 입력칸까지 문자 단축키로 가로채면 안 된다.
- **근거:** `DetailWorkspace.tsx`와 App/상세 테스트. 모든 플랫폼에 Q/E/A/D를 무조건 강제하는 근거는 아니다.

## E06. 미리보기 꺾쇠 버튼의 반복 수정

- **상황(T0):** 버튼의 세로 중앙이 틀리고 이미지 밖으로 나가며 둥근 배경이 주변 UI와 어울리지 않았다.
- **명시 요구:** 배경 없는 꺾쇠, 주변 UI와 조화, 호버 피드백. 후속으로 흰 이미지에서 더 잘 보이게 두께·테두리·그림자 보완, 호버하는 동안 커진 상태 유지.
- **이번 해석:** 최소한의 외형과 충분한 식별성은 함께 만족해야 한다. 배경을 없애는 것만으로 완료가 아니다.
- **현행:** `.preview-window-arrow`, `.preview-chevron-outline`, `.preview-chevron-mark` 및 1.16배 호버 확대.

## E07. 작가 폴더의 예열과 저장 재사용

- **요구(T0):** 작가별 보기에서 열지 않아도 표지·태그를 로드하고, 재실행 때마다 노출 후보를 탐색하지 않기. 이미 로드한 정보가 저장되는지 확인 후 코드 변경을 요구했다.
- **후속 배경(T1, 2026-09-20):** 썸네일 재사용과 무관한 과거 영상 전체 읽기는 과도하다고 지적. 턴 `01a0becb-4dbd-7771-b0bd-8731b11a4247`.
- **이번 해석:** 예열은 필요하되 원본 전체 검사나 무제한 동시 로드를 승인한 것은 아니다. 화면 준비와 제한된 백그라운드 예열을 구별한다.
- **근거:** `DownloadArtistFolderGrid.tsx`, `useSavedGalleryPreviews.ts`, `thumbnail/backgroundCoverPreloader.ts`, 최신 시작 성능 문서. 현재 관련 파일은 다른 작업의 미커밋 변경이 있다.

## E08. 요약 인덱스·점진 로드와 저장공간 표시

- **요구(T0):** 다운로드 목록이 커지며 진입 지연 발생. 요약된 작가·앨범 정보를 먼저 읽고 스켈레톤 표시 후 화면·스크롤 기준으로 로드하는 방향을 선택했다. 캐시/다운로드 용량과 디스크 공간 표시도 요청했다.
- **이번 해석:** 성능을 감추는 스켈레톤이 아니라 조작 가능한 골격과 국소 로딩이 필요하다. ‘계산 중’과 ‘0바이트’를 구별한다.
- **연결:** `ProgressiveGallerySlot.tsx`, `useProgressiveGalleryWindow.ts`, `SettingsDialog.tsx`. 요약 인덱스와 원본 파일 권한은 별개다.

## E09. 표지가 작가를 보여주어야 한다

- **상황(T0):** 한 작품 폴더 호버가 과도하게 크거나 무반응처럼 보임. 후기·텍스트 페이지만 있는 첫 페이지로는 작가의 작화를 파악하기 어려웠다.
- **명시 요구:** 정보칸이 아닌 표지에서만 호버, 원래 표지와 같은 크기로 수평 펼침, 한 작품도 그라데이션 반응. 자동 대표 선택을 기본으로 일부만 사용자 지정. 완료 후 후보 갱신·저장.
- **이번 해석:** 대표 이미지는 첫 페이지 고정이 아니라 탐색 판단을 돕는 자료다. 자동 판단의 오차를 수동 지정으로 보완한다.
- **한계:** ‘이전 요청에서는 3번’의 선행 제안 전문이 없어 구체 판별 알고리즘을 승인된 요구로 적지 않는다.

## E10. 공통 외형과 소스별 독립성

- **요구(T0):** Atsumi 배너로 소스 모드 전환 제안.
- **명시 요구(T3, 2026-09-01~02):** 공통/템플릿 공유/완전 분리 기능을 구분하고 설정을 일반/Hitomi/Danbooru로 분리. 카드 크기·로드 수도 각각 분리. 상세는 하단 시트가 아닌 플로팅 페이지. 고화질 포스터, 관계 목록, 상세 영상 자동재생도 요청했다.
- **턴:** `01a05bd9-2f1e-77c3-8f33-ed0be4f93b94`, `01a05e5e-a145-7bf0-8be0-f41096e7bf40`, `01a05b45-d557-7023-a2fd-28f641d4fc55`, `01a05e98-8a4e-7fe2-b126-801a503cc70c`.
- **당시 설명:** Hitomi는 앨범, Danbooru는 개별 post여서 정보 밀도와 저장 모델이 다르다. 목록 영상은 포스터로 자원을 절약하고 상세에서 재생한다.
- **결론:** 같은 톤과 조작 관례를 쓰되 데이터·크기·검색 문법을 억지로 통일하지 않는다. [Danbooru 명세](../DANBOORU_MODE.md).

## E11. 활동은 시간순만으로 충분하지 않다

- **상황·요구(T0):** 완료·진행·해시·검토가 섞여 복잡했다. 이번 실행에서 완료는 아래, 진행/검토는 위로 요청했다.
- **당시 대응:** 상태 우선순위와 그룹 내 최신순. 중복 처리된 실패 상태는 처리 완료로 해석.
- **후속 E12에 의해 보완:** 상단 우선순위 때문에 오래된 미완료 작업을 무한히 붙잡아두지는 않는다.
- **현행:** `ActivityDrawer.tsx`는 최신 50건을 먼저 뽑고 그 안에서 상태 정렬한다. 영구 자동분류 기록의 정렬은 별개다.

## E12. 최근 기록과 전체 작업 제어를 분리

- **상황(T2, 2026-09-22):** 취소하려는 작업이 실시간 목록에 없고, 활동 이름만으로는 작품을 알아보기 어려웠다.
- **사용자 요구:** 다중선택 바와 플로팅 상세에서 취소 가능하게 하되 활동 기록에 모든 작업을 계속 남기지 말 것.
- **턴:** `01a0c81b-cdf4-7c92-9444-e71b8cda7681`, `01a0c823-a46c-7c62-bb66-bd7218de5000`.
- **당시 대응:** 진행 상태의 상세 주 버튼을 취소로, 선택 바에 취소 가능한 개수 표시, 활동은 최근 50개. **50이라는 수치는 당시 구현 선택**이며 사용자의 직접 지정 숫자는 아니다.
- **현재 확인:** `RECENT_ACTIVITY_LIMIT = 50`, 최신창 선택 후 상태 정렬.
- **미해결:** 활동 행의 표지/작가 정보 확충은 별도 제안. 전체 대기열 복원 제안은 사용자의 ‘너무 많다’는 후속 결정을 무시하고 되살리지 않는다.

## E13. 자동화 뒤에도 사람이 검토할 수 있어야 한다

- **요구(T0):** A/B 상하 대응, 추가 페이지 강조, 다크 표면, 명확한 버튼과 짧은 설명, 호버 확대, 최종 선택 자체를 로컬 정답으로 기록. 자동분류 근거에서 복원·확인 완료·순차 검토.
- **후속(T1, 2026-09-22):** 자동분류 완료 후 이미 격리된 원본을 미리보기로 확인할 수 없었다. 처음에는 개선 의견, 다음 턴에는 구현 요청.
- **턴:** `01a0c86d-3ae5-7e51-97ae-c923ba087fef`, `01a0c8d5-1e7b-7972-a182-c6da5282dbbd`.
- **당시 설명:** 일반 이미지 로더가 격리 상태를 거절해, 파일이 있어도 표시하지 못했다. 검토 전용 읽기로 제외 해제 없이 원본을 보여주는 방식을 채택했다.
- **이번 확인:** 검토 컴포넌트에 ‘복원 없이 비교’ 및 ‘없거나 변경됨’ 안내, `overlap_review_thumbnail.rs` 신규 경로가 있다. 현재 코드의 존재를 확인했으며 실제 원본 열람을 재시험하지 않았다.
- **경계:** 목록 복원≠파일 복원, 남은 원본 읽기≠판정 당시 이미지 영구 보존. 임계값은 별도 도메인 규칙이며 디자인 시스템에서 재정의하지 않는다.

## E26. 정상 준비 중 안내를 오류와 구별

- **요구(T0, 2026-09-23):** 로딩서클 표시 기준을 질문한 뒤, 녹화 탭 최초 진입의 ‘목록 준비 중·다른 탭 이용 가능’ 안내가 정상 동작인지 빨간 오류인지 구분하기 어렵다며 개선 요청.
- **실제 원인:** `startup.rs`는 준비 중을 `BROWSER_INITIALIZING`, 초기화 실패를 `BROWSER_UNAVAILABLE`로 구별한다. `OfficialBrowserPanel.tsx`는 오류 코드를 버리고 메시지만 보관하여 둘 다 빨간 `role=alert`로 표시했다. 최초 성공 전에도 ‘마지막 확인 상태’ 문구를 붙였다.
- **추가 확인:** 카드의 요약 정보 확인 전 `summaryPending` 항목이 임시 `interrupted` 상태 때문에 확인 필요로 분류될 수 있었다. 정상 녹화의 빨간 점과 오류의 빨간 점도 구별되지 않았다.
- **조치:** 준비 중/지연은 청록 상태 표시, 상태 확인 실패는 주황 주의, 실제 초기화 실패는 빨간 오류로 분리. 최초 성공 전 빈 목록을 숨기고, 갱신 실패 때는 기존 목록을 유지하며, 복구 성공 시 안내 제거. 카드도 대기·처리·완료·주의·실패를 문구와 기호로 구별.
- **구현 선택:** 250ms 표시 지연과 20초 지연 안내는 사용자가 지정한 수치가 아니라 이번 구현값이다. 문구는 짧게 유지하고 상세는 호버/포커스로 제공한다. 단순히 시간이 지났다고 실패로 단정하지 않는다.
- **범위:** 녹화 탭에 적용하고 공통 표시 계약은 명세 C06에 기록했다. 앱 전역의 모든 상태 UI를 이미 바꿨다는 의미는 아니다.

- **탐색 연속성:** Danbooru는 첫 방문 이후 소스·커뮤니티 전환 때 목록과 스크롤을 유지한다. 숨긴 상세의 영상·키보드 처리는 중지한다. 태그·새 검색에서 최대 12개의 이전 탐색을 되돌릴 수 있고 검색 16페이지/다운로드 8페이지의 메타데이터 캐시를 둔다. 이 결과 캐시는 현재 실행 중에만 유효하며 디스크 영구 보존이나 RAM 사용량 보장을 의미하지 않는다.
- **상태·알림:** 자동 녹화·내 채널·계정 확인의 초기화를 실제 실패와 분리. 앱 시작 상태 조회 실패를 침묵하지 않고 자동 재확인으로 표시. Danbooru 결과 알림은 애니메이션 이벤트 대신 4초 타이머로 제거.
- **밀도·접근성:** Danbooru 검색 문법과 판본 제거의 기술 설명은 접힌 상세로 이동하되 파일 보존/미복원 같은 필수 결과는 본문에 유지한다. 설정 관리 버튼은 문구 폭·34px 최소 높이로 축소. 공통·관계 로더는 동작 감소 설정에서 회전만 제거한다.
- **경계:** 사용자 다운로드·녹화 데이터, 백엔드 판정 정책, 배포 상태는 이번 UI 정비로 바꾸지 않는다. 모든 디자인 제안이나 후순위 테마까지 구현한 것은 아니다.
