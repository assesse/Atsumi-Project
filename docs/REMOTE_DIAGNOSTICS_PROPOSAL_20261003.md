# 원격 실시간 진단 과거 검토안

2026년 10월 4일 사용자는 원격 실시간 열람 대신 사용자 직접 공유 방식으로 방향을 바꿨다. 현재 구현 범위는 앱 전반의 기본 진단과 로컬 순환 로그뿐이다. 문제 재현 모드·내보내기·전송·서버 접근은 아직 구현하지 않는다. 현재 기준은 [로컬 기본 진단과 즐겨찾기 단순화](LOCAL_DIAGNOSTICS_20261004.md)를 따른다.

아래는 10월 3일 검토한 원격 방식의 비용·권한·위험을 보존한 참고 자료이며 적용 지시가 아니다. 원격 진단 서버·계정 권한·업로드는 변경하지 않았다.

## 권장 사용 흐름

1. 다른 PC에서 사용자가 설정의 원격 진단 시작을 누른다. 수집 항목과 보관 기간을 표시하고 동의를 받는다.
2. 30분짜리 지원 세션을 발급한다. 화면에는 지원 번호와 남은 시간, 즉시 종료 버튼을 표시한다. 하드웨어 식별자를 수집할 필요는 없다.
3. 앱은 허용된 필드만 HTTPS로 서버에 전송한다. 읽기 권한은 앱의 업로드 권한과 분리한다. 서버 장애가 다운로드나 녹화를 지연시키지 않게 한다.
4. 개발자는 인증된 조회 도구에서 해당 지원 세션을 선택한다. 지원 번호 자체는 비밀번호가 아니며, 번호만 안다고 타인의 로그를 읽을 수 없어야 한다.
5. Codex는 세션 요약, 시간순 이벤트, 특정 작업의 단계만 조회한다. 원격 PC의 임의 파일·DB·명령 실행 권한은 제공하지 않는다.
6. 세션 종료·동의 철회·만료 시 신규 전송을 중단한다. 예를 들어 서버 자료는 72시간 후 자동 삭제한다. 이는 제안값이며 사용자가 보관 정책을 승인한 뒤 적용한다.

Codex에서 직접 조회하려면 별도의 연결이 필요하다. 로그 서버를 만든 것만으로 현재 채팅이 그 서버나 다른 PC에 자동 접근할 수 있는 것은 아니다. 인증된 MCP 조회 도구를 제공하는 구성이 가능하며, 서버가 매 요청마다 실제 접근 권한을 검증해야 한다. 도구를 읽기 전용으로 표시하는 것만으로 접근 통제가 생기지는 않는다. [OpenAI 공식 MCP 구현 문서](https://developers.openai.com/plugins/build/mcp-server), [인증 문서](https://developers.openai.com/plugins/build/auth).

## 수집할 정보와 제외할 정보

| 기본 수집 후보 | 기본 수집 금지 |
|---|---|
| 앱 버전, 빌드 식별자, OS 및 WebView 버전 | 로그인 쿠키, Authorization 헤더, 비밀번호, 커뮤니티 작성자 키 |
| 시작 단계와 소요 시간, DB schema 버전 | 사용자 DB 전체, 다운로드 목록 전체, 앨범 제목과 검색어 |
| 작업별 임시 식별자, 단계, 진행량, 경과시간, 오류 코드 | 원래 갤러리 ID, 원본 미디어, 채팅 내용, 전체 요청 URL과 쿼리 |
| 사이트 호스트와 요청 종류, HTTP 상태, DNS/TLS/timeout 구분 | 사용자명 포함 파일 경로, 설치 계정명, 원격 제어 토큰 |
| CPU/메모리 집계, UI 응답 지연, 큐 개수 | 키 입력 내용, 전체 메모리 덤프, 화면 녹화 |

갤러리 ID도 이용 기록을 드러낼 수 있으므로 기본은 세션 안에서만 통하는 임시 식별자로 대체한다. 특정 작품 문제를 확인하려면 사용자가 직접 번호를 전달하거나 해당 세션에서 추가 수집에 동의하도록 한다. 서버에 도착한 뒤 가리는 것이 아니라 앱에서 전송 전에 필드를 제한해야 한다.

## 예상 문제와 대응

- **정보 유출과 권한 분리:** 지원 사용자별 자료가 섞이면 안 된다. 짧은 수명의 업로드 전용 토큰, 개발자 인증, 세션별 조회 권한, 감사 로그가 필요하다. 관리자 키를 앱에 내장하면 안 된다.
- **모든 원인을 즉시 알 수 있는 것은 아님:** UI가 멈추거나 앱이 실행조차 못 하면 앱 내부 전송도 멈출 수 있다. 네이티브 시작 단계부터 작은 로컬 순환 로그를 남기고, 유효한 동의가 있는 다음 실행에서 보충하는 경로가 필요하다. 설치 프로그램 단계의 실패는 별도 설치 로그가 필요하다.
- **네트워크 문제:** 서버 접근이 막힌 PC의 로그는 실시간 전송되지 않는다. 로컬 저장과 재전송, 마지막 수신 시각 표시가 필요하다. 수신이 없다는 것을 오류가 없다는 뜻으로 해석해서는 안 된다.
- **로그가 앱을 느리게 만드는 문제:** 이미지마다 파일 동기화나 서버 요청을 하면 기존 다운로드 성능을 해칠 수 있다. 비차단 기록 큐, 2~5초 단위 묶음 전송, 크기 제한, 반복 오류 집계와 드롭 카운터를 사용한다. 재시도 횟수도 제한한다.
- **용량과 비용:** 이미지를 안 보내도 초당 로그를 무제한 보관하면 커진다. 가령 한 건이 1KB이고 초당 한 건이면 PC 한 대에 하루 약 86.4MB, 100대면 약 8.64GB다. 압축·인덱스·통신 오버헤드를 제외한 예시 계산이며 실제 사용량 예측이나 무료 보장은 아니다.
- **서버 운영:** 만료 자료 삭제, 인증키 교체, 접근 이력, 비정상 업로드 차단, 서버 장애 대응이 필요하다. 읽기 및 쓰기 속도 제한과 세션당 저장 상한을 둔다. 커뮤니티 서비스와 권한·테이블·할당량을 분리한다.
- **AI가 로그를 지시로 오인할 위험:** 외부 오류 메시지나 텍스트는 신뢰할 수 없는 데이터다. 로그 도구에 임의 명령 실행 기능을 넣지 않고, 도구 응답에서도 데이터임을 명시한다.
- **상시 감시와 진단은 다름:** 서버에 실시간 로그가 쌓여도 Codex가 계속 열람하거나 자동으로 수정하는 것은 아니다. 이 채팅에서 조회 요청을 받았을 때 접근하는 것이 1차 범위다. 자동 감지·알림·수정은 별도 설계와 권한이 필요하다.

## 기존 Supabase 사용 시 경계

기존 커뮤니티의 공개 후기 권한을 진단 자료에 재사용하면 안 된다. 진단 테이블은 비공개이며 세션별 권한이 필요하다. Supabase의 RLS와 Realtime authorization은 이러한 접근 경계를 만드는 수단이지만, 정책을 직접 설계하고 다른 세션 접근이 거절되는지 테스트해야 한다. [RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security), [Realtime 권한 문서](https://supabase.com/docs/guides/realtime/authorization).

처음부터 모든 로그를 실시간 DB 구독으로 보내기보다는 제한된 수집 API와 읽기 API로 시작하고, 상태 요약만 실시간으로 갱신하는 편이 단순하다. DB와 전송 비용을 측정한 뒤 필요하면 원문 로그를 별도 저장소로 분리한다. 이번 검토에서는 특정 요금제의 무료 한도나 비용을 확정하지 않았다.

## 단계별 구현 제안

먼저 로컬에서 동일한 진단 이벤트 모델을 정한다. 파일 저장, 원격 전송, 나중의 진단 파일 내보내기가 그 모델을 공유하도록 하면 원격 방식을 폐기해도 수집 코드를 다시 만들 필요가 없다.

다음으로 제한된 테스트 PC에서만 동의형 지원 세션을 시험한다. 권한 경계, 민감정보 제거, 서버가 꺼져도 앱이 정상 동작하는지, 앱 강제 종료 뒤 로그가 어디까지 남는지 검증한다. 그 뒤 Codex의 읽기 전용 도구 연결을 추가한다. 연결 및 인증 설정은 배포 앱 수정과 별도의 작업이다.

실제 적용 전에 정할 사항은 운영할 서버/프로젝트, 개발자 조회 계정, 기본 전송 항목, 세션 시간과 보관 기간이다. 현재 제안은 30분 세션과 72시간 자동 삭제이며 원격 PC 제어·자동 명령 실행·상시 업로드는 범위에 포함하지 않는다.
