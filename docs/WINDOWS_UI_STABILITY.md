# Windows 창 응답·크기 변경 점검 (2026-09-12)

## 창을 찾을 수 없었던 직접 원인

실제 사용자 세션에서 Atsumi 주 창은 **최소화 + 응답 없음**이었다. 창,
트레이, 단일 인스턴스 창 모두 같은 UI 스레드에서 멈췄다. 격리된 진단
세션에서는 창 핸들이 0으로 보였으므로, 그 결과만으로 숨김/화면 밖 이동을
원인으로 판단하면 안 된다.

전체 메모리를 덤프하지 않고 멈춘 스레드의 호출 위치를 읽었다:

```text
Tao keyboard callback (KEY_EVENT_BUILDERS 잠금 보유)
  KeyEventBuilder::process_message
    PeekMessageW
      동기적으로 재진입한 Tao keyboard callback
        KEY_EVENT_BUILDERS 잠금 대기
          WaitOnAddress (진행 불가)
```

CPU 과부하나 녹화 저장 지연이 아니라 Windows 입력 처리의 재진입 교착이다.
사용자가 진행 중 작업이 없다고 확인하고 종료를 허용한 후, 식별한 Atsumi와
그 개발 실행기 자식 프로세스만 종료했다. 탐색기나 다른 작업은 종료하지 않았다.

현재 runtime이 사용하는 Tao 0.35.3에 [공식 수정 #1215](https://github.com/tauri-apps/tao/pull/1215),
commit `c704261c`의 Windows 입력 파일 네 개를 그대로 백포트했다. 키보드·IME
다음 메시지 조회를 잠금 밖으로 옮긴다. 더 큰 API/입력 구조 변경을 포함하는
Tao 0.36으로 전체 교체하지 않았다. 출처·라이선스는 `src-tauri/vendor`에 보존한다.

회귀 검증은 실제 vendor IME 상태 머신의 한글·UTF-16 처리와 입력 잠금 경계를
검사한다. 원래 잘못된 잠금 순서를 테스트용 소스에 재도입하면 검사에서 거부한다.

별도의 숨김 native 창 `windows_input_probe`에서도 키 down/up 처리 중 다른
스레드가 보낸 포커스 메시지를 실제로 재진입시켰다. 8회 재진입·반환, 4회 문자
전달이 모두 완료됐다. 실제 사용자 입력, WebView, 계정, DB는 사용하지 않는다.

바탕화면 개발 실행기는 기존 프로세스가 있으면 조용히 종료하는 대신, 제한 시간
내 창 응답을 확인하고 기존 창을 복원한다. 응답 없는 앱은 안내만 하며 자동으로
녹화나 프로세스를 강제 종료하지 않는다.

## 크기 변경: 확인한 사실과 구분해야 할 것

- CHZZK React 화면은 Hitomi/Danbooru 전환 시 해제된다. CHZZK 화면의 모든
  observer가 다른 소스에서도 계속 실행된다는 추측은 코드와 맞지 않았다.
- 단일 시청 패널의 녹화 보관함/비활성/닫힘/프라이버시 상태에서는 숨김 경계만
  한 번 전달하고 문서 전체 변경 및 조상 크기 관찰을 설치하지 않도록 수정했다.
- 카드 크기가 픽셀 단위로 바뀔 때마다 숨겨진 태그까지 펼쳐 측정하고 다시 접는
  작업이 반복됐다. 태그 정렬 결과와 썸네일 키를 재사용하고, 무거운 태그·행 높이
  측정만 마지막 크기 변경 후 100ms로 모았다. CSS와 열 수 전환은 즉시 반응한다.
  그리드가 태그 DOM 변경과 자신이 쓴 높이에 반응해 전체 카드를 재측정하는
  경로도 제외했다. 이미 로드된 카드나 이미지 캐시를 언로드하는 변경은 없다.
- 합성 60개 카드·25회 크기 변경 회귀에서는 드래그 구간 태그/전체 그리드
  재측정 0회, 안정화 후 한 차례 측정, 썸네일 재구독 0회를 확인했다.
  최초 태그 표시, 이미지 고유 크기 변경, 카드 추가, 열 경계 전환은 유지된다.
- `main_resize_probe`는 합성 페이지와 별도 프로필로 기존 Tauri child autoresize와
  직접 WM_SIZE 처리를 비교했다. 6개 경우·540회 크기 변경 모두 통과했다.
  기존 경로의 native 확인 p95는 4.08–5.12ms, 직접 경로는 4.02–4.56ms였다.
  이 측정에서는 직접 경로로 교체할 근거가 없었다.
- 위 측정은 **프로그램 방식 크기 변경 확인 시간**이며, 실제 수천 장의 카드가
  있는 화면에서 사용자가 마우스로 끌 때의 프레임 시간은 아니다. 이 결과를
  사용자 환경 전체의 렉 해소나 실측 FPS 개선으로 표현하지 않는다.

광고 필터의 별도 적용 범위·실방송 미검증 한계는 `CHZZK_VIDEO_ADS.md`에 기록했다.

## 검증 결과

- 최종 프런트엔드: 93개 파일, 860개 테스트 통과; 타입 검사·번들 빌드 통과.
- Rust 전체 library: 653개 통과, 17개 opt-in 검사 제외. 이후 추가된 광고 응답
  헤더 변경까지 포함한 광고 회귀 테스트 8개 별도 통과.
- 실제 WebView2 광고 필터 합성 검증: 14개 요청 결과 통과. 외부 네트워크·계정 미사용.
- Windows 입력 재진입, native 크기 변경 검증 및 개발 실행 파일 빌드 통과.
