# CHZZK 공식 시청 창·화면 녹화 프로토타입

작성: 2026-09-11, 현재 상태 갱신: 2026-09-12. 정식 배포·릴리스가 아닌 개발용 프로토타입 명세다.
현재 시청 경로는 공식 페이지·마도다. 구형 HLS 수신/재생 UI는 제거했으며 기존 파일은 삭제하지 않았다. 실서비스 지연·그리드 호환·장시간 무손실을 보장하지 않는다.

병합 worker의 host 수명 연결과 관리형 FFmpeg/ffprobe 준비·실행 버전 확인을 완료했다. 2026-09-12 최종 자동 검증은 프런트엔드 91개 파일/831개 테스트, typecheck, Vite build, Rust library 615개/main 2개 테스트가 통과했다. 기본 Rust 실행의 ignored 17개 중 FFmpeg E2E 3개는 별도로 실행하여 통과했다. debug `cargo build`도 2026-09-12 13:06:54 KST에 성공했다.

병합 E2E는 실제 `EncodedMuxer`를 거친 합성 MP4 2조각의 병합·전체 디코딩·원본 보존, duration 메타데이터가 없는 합성 WebM의 한국어 경로/1·2조각/읽기 전용 원본/전체 디코딩, 손상 입력 거절과 취소를 확인했다. 합성 검증이며 실제 CHZZK 광고·방송, 사용자 계정·미디어 검증은 아니다. 사용자 파일의 병합·백필은 이번 검증에서 실행하지 않았다. 네이티브 팝업의 격리 합성 영상 probe도 통과했지만 실제 CHZZK 방송·오디오·녹화 연속성 검증은 아니다. 아래 날짜별 이전 테스트 기록도 이번 변경의 실사용 검증 결과와 구분한다.

격리 팝업 probe는 exit 0, `success: true`로 끝났고 `currentTime`이 1.202102→3.400336초(2.198234초 진행), `paused=false`, `visibility=visible`이었다. 모달 동안 영상 bounds 유지·입력 차단·신뢰된 메인 화면으로의 포커스 반환, 스크롤 120회의 SHOW/HIDE 이벤트 0회, 의도적인 hide/show 및 stale/invalid 요청 차단·복원을 확인했다. 종료 후 probe 잔존 프로세스는 0개였다.

## 공식 페이지와 로그인

- `CHZZK 공식 시청`에서 채널 URL/ID를 입력하면 메인 창 안의 별도 child WebView 한 개에 공식 플레이어와 공식 채팅을 함께 연다. iframe이나 Chrome 원격 제어가 아니다.
- 실제 CHZZK 페이지의 로그인·영상 플레이어·공식 채팅 UI를 사용한다. Chrome 자체가 아니라 Windows WebView2다.
- 첫 시청 시 CHZZK의 확장 안내가 표시되면 공식 페이지에서 `설치없이 일반 화질 시청`을 선택할 수 있다. 앱이 화질 선택·로그인·확장 설치를 자동으로 진행하지 않는다.
- 로그인·본인인증은 명시적으로 임시 창을 열어 진행하며 공식 시청 WebView와 동일한 전용 프로필 세션을 사용한다. 계정·치트키·타임머신 권한은 공식 페이지에서 확인한다.
- Chrome/Edge의 계정 쿠키나 전체 프로필을 읽거나 복사하지 않는다. 공식 로그인 세션은 별도 WebView2 프로필에 보관된다.
- 로그아웃은 확인 후 전용 프로필의 로그인 세션을 지우는 작업이며 녹화 중에는 막는다. 다른 브라우저의 계정과 녹화 파일은 대상이 아니다.
- 스크롤·창 크기 변경은 전체 페이지 viewport 크기를 보존한 네이티브 clipping으로 맞춘다. 표시를 가리는 것과 영상 소스/녹화 수명을 종료하는 것은 별개이며, 메뉴·설정 때문에 녹화를 다시 시작하지 않는다.
- 단일 시청의 자체 `간단히 보기`/`전체 보기`와 페이지 재배치 스크립트를 제거했다. 공식 플레이어의 `넓게`/`좁게` 버튼과 페이지 배치를 그대로 사용한다. 마도의 pane 배치는 별도 스크립트이므로 제거 대상이 아니다.
- 설정 gear는 공식 LIVE 표시의 옆에 안정적으로 붙인다. 해당 컨테이너가 없으면 영상 안의 겹치지 않는 위치를 사용한다. LIVE의 클릭 동작/재생 상태 의미를 바꾸지 않는다. 채팅 placeholder·입력 높이·스타일은 수정하지 않으며, 끝점까지의 거리는 배속 버튼 도움말에 표시한다.
- 창 열기·앱 시작·모드 진입으로 자동 녹화하지 않는다. 저장 권한과 이용 조건을 확인한 뒤 사용자가 시작한다.
- 로그인·유료 권한·DRM 등 접근 제한을 우회하지 않는다. 캡처를 지원하지 않는 영상은 실패로 안내한다.
- 원격 페이지의 Tauri IPC(내부 데이터 채널 포함)는 vendored Tauri의 네이티브 경계에서 차단한다. 녹화는 출처·사용자 시작 nonce·세션을 검증하는 별도 접두사 메시지만 수신한다. 패치는 `src-tauri/vendor/ATSUMI_PATCHES.md`에 기록한다.

### 개발판에서 확인하는 순서

1. 바탕화면 `Atsumi` 바로가기로 2849 공유 작업공간의 개발 앱을 연다.
2. CHZZK에서 채널 주소를 입력하고 `시청 시작`을 누른다. 이미 시청 창을 열었다면 주소·계정 조작은 `설정`에서 찾는다.
3. 공식 LIVE 옆 gear로 설정을 열어 `고화질 연결`과 실제 해상도를 확인한다. 네이버 연결 프로그램과 공식 확장이 이미 설치되어 있어야 한다.
4. 계정이 필요하면 `설정`의 `로그인`으로 임시 창을 연다. 기존 Chrome 계정이 자동 복사되는 것은 아니다.
5. 저장 권한과 이용 조건을 확인하면 `녹화 시작`이 밝은 민트색으로 활성화된다. 녹화가 시작되면 붉은 `녹화 중지`로 바뀐다. 일반 채팅 저장은 설정에서 선택하며, 영상·채팅 각각의 상태를 확인한다.
6. `?` 도움말은 마우스 호버·키보드 포커스에서 보이며 Esc 또는 스크롤로 닫힌다. 실제 시청 영역을 덮는 경우에만 네이티브 화면을 가린다. 오류·녹화 중단 조건·저장 권한 확인은 도움말에만 숨기지 않는다.

## 같은 재생 영상에서 녹화

현재 구현은 지원되는 메인 문서 MSE의 clear AVC/H.264 + AAC-LC fMP4 데이터를 이미 받은 append에서 분기하는 경로와, 지원되지 않을 때의 1배속 화면 재인코딩 경로를 구분한다. 세부 지원 조건은 [플레이어 확장 명세](CHZZK_PLAYER_EVOLUTION.md)에 있다. raw 수신/컨테이너 지원을 확인하지 않고 배속 옵션만 푸는 방식이 아니다.

지원·native 승인이 확인된 동일 영상의 encoded 녹화에만 1.2배 따라잡기를 허용한다. MediaRecorder fallback 녹화에서는 배속을 계속 막는다. 이번 UI 정리에서 이 안전 조건은 완화하지 않았다. 버퍼 부족·일시정지·탐색·영상 교체 등의 조건에서도 따라잡기를 끝내며, 송출/CDN의 절대 지연을 제거하는 기능은 아니다.

아래 항목은 **화면 재인코딩 fallback**의 동작이다.

- 공식 페이지가 재생하는 `HTMLVideoElement.captureStream()`을 `MediaRecorder`에 전달한다.
- 녹화를 위해 별도 Rust HLS 수신기를 추가 실행하지 않는다. 영상 수신은 공식 플레이어 경로를 사용한다.
- 다만 공식 플레이어의 자체 재요청·화질 전환·P2P 업로드까지 트래픽 0으로 제어한다는 의미는 아니다.
- 채팅 저장은 공식 페이지가 이미 사용하는 소켓의 수신 메시지를 관측한다. 별도 채팅 연결은 만들지 않으며, 방송 업타임 계산용 공개 메타데이터만 추가 조회한다.
- 원본 영상 조각을 그대로 저장하는 방식이 아니다. 재생된 영상·음성을 다시 인코딩하므로 CPU/GPU 부하와 품질 손실이 생길 수 있다.
- 현재 인코딩 요청값은 영상 8 Mbps, 음성 128 kbps이며 실제 출력은 WebView2·코덱·시스템 상태에 따라 달라진다.
- 지원되는 WebM/MP4 코덱을 선택하며, 재생 가능한 영상·음성 트랙이 없으면 정상 녹화로 취급하지 않는다.
- 공식 웹과의 지연 차이가 1초 이내라는 보장은 없다. 동일 방송·동일 시점·동일 화질에서 직접 측정해야 한다.
- 그리드 사용 여부, 버퍼, 디코딩·재인코딩 부하를 분리해 측정해야 지연 원인을 판단할 수 있다.

## 파일 회전과 중단 조건

- fallback은 약 15초마다 MediaRecorder를 종료·재시작하여 각각 독립적으로 마무리된 영상 파일을 만든다. encoded 경로는 약 12초 이후 키프레임 경계로 파일을 마감하며 지원하지 않는 변화는 중단으로 표시한다.
- 인코더 회전 경계에 영상·음성 공백이 생길 수 있으며, 프레임 단위 연속성이나 원본과의 비트 단위 동일성을 보장하지 않는다.
- 15초는 타이머 목표값이다. 최소화·백그라운드 타이머 제한·시스템 부하에서는 늦어질 수 있는 best-effort 동작이다.
- 다른 Atsumi 모드로 이동하거나 창을 최소화하는 것만으로 중지 명령을 보내지 않는다.
- 공식 페이지 새로고침·닫기·이탈, 채널/영상 교체, 과거 탐색은 중단 조건이다. fallback에서 1배속이 아닌 값으로 변경하면 중단하며, encoded의 검증된 동일 영상 배속 허용과 구분한다. encoded도 탐색·일시정지는 연속성을 보장할 수 없어 중단한다.
- 녹화 중 타임머신을 사용하려면 먼저 녹화를 끝내야 한다. 시청 위치와 무관하게 라이브 끝을 계속 저장하는 독립 수신기는 아니다.
- 저장 지연·대기열 초과·인코더 오류·영상/음성 소실·네이티브 연결 실패도 중단 사유다.
- 정상 중지는 마지막 파일 마무리를 기다린다. 강제 종료·페이지 종료·전원 장애 시 마지막 파일은 불완전할 수 있다.
- 별도 녹화 프로세스가 아니므로 WebView2/앱 프로세스 종료 후에도 계속 녹화되는 구조는 아니다.

## 보존 구조와 녹화 목록

- 저장 위치는 설정된 다운로드 루트 아래 `CHZZK/BrowserCapture/<recording-id>/`다.
- `recording.json`에 세션 상태, `segments.jsonl`에 확정된 영상 파일의 전체 인덱스를 기록한다.
- 검증된 병합 완료 기록은 `영상 열기`로 기본 외부 플레이어에서 재생한다. 대기/진행/실패 상태를 구분하고 실패 기록은 재시도를 제공한다. 원본 조각은 접힌 목록에 보존하며 개별 열기도 유지한다. 전체 인덱스를 계속 RAM/DOM에 쌓지 않고 최신 128개 세그먼트만 snapshot에 유지한다.
- 다음 앱 실행부터 보관함의 확정 조각이 있는 종료 기록을 하나의 공유 worker가 자동 병합 예약하며, 새 녹화 종료 후에도 같은 worker를 깨운다. 녹화 중 파일은 병합하지 않고, 원본 영상·저널·채팅 파일을 삭제하거나 재작성하지 않는다. 형식/도구/공간 등의 검증에 실패하면 완성본으로 처리하지 않는다. 이는 이번 검증에서 사용자 파일의 병합·백필을 실행했다는 뜻이 아니며, 구형 HLS 파일을 자동 이관하는 기능도 아니다.
- 목록 밖의 이전 파일도 자동 삭제하지 않는다. 전체 파일과 저널은 녹화 폴더에서 확인한다.
- 카탈로그는 앱 데이터의 별도 `streaming/browser/catalog.jsonl`에 보관하며 최대 256개다.
- 현재는 256개를 자동 순환·삭제하지 않는다. 한도에 도달하면 신규 녹화를 거절하는 제한이 있다.
- 확정되지 않은 `.partial` 또는 저널 기록 전 중단된 파일은 별도로 보존·표시하며 완성 파일로 성공 처리하지 않는다.
- 재시작 시 확정 저널을 재구성한다. 중단·손상 상태를 알리고, 기존 녹화 파일을 수정하거나 정상 종료로 위장하지 않는다.
- 기존 사용자 DB와 기존 HLS 녹화는 이 경로로 이전·덮어쓰기·초기화하지 않는다.

## 공식 채팅과 저장된 채팅은 구분

- 시청 중인 공식 페이지가 받은 일반 라이브 채팅(type 1)을 녹화 시작 후부터 저장한다. 이전 기록 요청·후원/인증/제어 프레임은 저장 대상이 아니다.
- 로그인·성인 인증 여부는 공식 페이지가 처리한다. 소켓 송신 내용이나 쿠키·토큰을 읽거나 Rust 수신기로 전달하지 않는다.
- 닉네임·메시지·시간·표시용 배지/이모티콘만 정규화한다. 다른 채널의 이전 소켓은 새 녹화에 포함하지 않는다.
- 총 200개 제한은 없다. 최대 32개/128 KiB 배치마다 디스크 동기화 후 ACK하고, 중지는 승인된 채팅 배치 마무리 후 영상 파일을 끝낸다.
- 메모리 대기열은 2 MiB로 제한한다. 연결 공백·지원하지 않는 프레임·대기열 초과·저장 실패를 별도로 표시하며 영상 녹화와 오류를 분리한다. 누락 표시는 전체 누락량의 정확한 계수가 아니다.
- 녹화 경과와 가능한 경우 방송 업타임을 기록한다. 공개 메타데이터에서 방송 시작 시간을 구하지 못했거나 조회 완료 전이면 해당 메시지 업타임은 미상이다.
- `chat.jsonl`을 녹화 폴더에 저장한다. 현재 공식 녹화 목록에는 전용 채팅 로그 뷰어가 없다.

## 구형 HLS 제거와 검증 범위

- 구형 HLS 연결·수신·재생 UI/API 및 기존 채팅 패널/페이지 훅을 제거했다. 라이브/보관함은 공식 시청 경로를 사용하며 마도는 별도로 유지한다. 구형 녹화 파일·JSONL·사용자 DB는 삭제하거나 자동 이관하지 않았다.
- `hls.js`는 제품 재생 경로에서 제거하고 압축 녹화의 합성 fMP4 fixture 생성용 개발 의존성으로만 남겼다. 구형 HLS WebView probe는 제거했다. [CHZZK.md](CHZZK.md)는 당시 구현/검증의 역사 기록이다.
- 브라우저 미리보기에서는 공식 연결/녹화를 실행하거나 성공한 것처럼 모의 데이터로 표시하지 않는다.
- 자동 검증 대상: 시작 권한·중복 요청·출처 제한·늦은 응답·중지 순서·대기열 한도·채팅 독립성·모드 격리.
- dock UI 검증 대상: viewport 좌표·scroll clipping·최신 크기 coalescing·늦은 unmount 숨김·모달/프라이버시/경로 가림·로그아웃 확인·공식 페이지 조작 유지. 모의 DOM 검증은 실제 WebView2 포커스·DPI·공식 로그인 검증을 대체하지 않는다.
- 저장 검증 대상: 중복 chunk·저널 commit·손상/중단 복구·partial 보존·기존 파일 보호·경로/크기 제한.
- 확장 검증 대상: 지정 프로필/ID·버전·공개키 해시·경로 탈출/reparse·용량 제한·콜백 처리.
- 모의 테스트 통과만으로 실제 CHZZK 로그인·그리드·인코더·음성·장시간 연속 녹화를 검증했다고 주장하지 않는다.

## 2026-09-11 스크롤·버튼·UI 간소화 수정

- 임시 about:blank 프로필에서 설치된 Chrome 공식 확장 로드 및 `sendNativeMessage` 커넥터 초기 응답 성공. 이것만으로 장기 그리드 포트나 고화질 재생을 보증하지 않는다.
- 공개 일반 방송에서 공식 페이지의 확장 감지 성공. 명시적 일반 화질 선택 후 853×480 재생과 프레임 증가, `clean` 배치의 플레이어 947×800 / 채팅 333×800(1280×800 viewport)을 확인했다.
- 본인 계정 로그인·19세 방송 및 장시간 녹화는 별도 실기 검증이 필요하다.
- 추가 A/B 검사: 같은 공개 일반 방송에서 Edge UA + Chrome 확장은 설치 안내에 멈췄다. 실제 Chromium 152 버전을 유지하고 Edg 토큰만 제거하자 1920×1080, readyState 4, paused=false, 디코딩 프레임 109→1369 증가를 확인했다. 사이트의 로컬 네트워크 권한 안내는 숨기거나 자동 승인하지 않는다.
- 최종 제품 연결 경로(`--chrome-identity` 없이)에서도 1920×1080, readyState 4, paused=false, 디코딩 프레임 110→1369 증가와 정상 종료를 확인했다. 추가 검사에서 사이트의 정확한 설명용 `alertdialog`의 확인 버튼만 한 차례 누른 뒤 `clean` 배치 복귀와 공식 채팅 333×800을 확인했다. 이 후자의 화면 검사는 공식 광고 재생 중이었으며 브라우저 네트워크 권한 부여나 광고 건너뛰기를 수행하지 않았다.
- 실제 검사에서 발견한 확장 완료 콜백의 Tauri 재진입 잠금도 수정했다. 위 전체 검사 이후 관련 16개 테스트(새 재진입 회귀 1개 포함)를 다시 통과했고 앱·격리 검사 도구를 재빌드했다. 검사 도구에는 60초 종료 제한을 추가했다.
- 프런트엔드 최종 전체 89파일·715개 통과, TypeScript·Vite 빌드 통과. 1440×900 및 900×720 브라우저 미리보기에서 설정 펼침 시 높이 겹침을 보정했다. 실제 Tauri 최소 너비는 960px이다.

최초 별도 창 프로토타입의 이전 검증 기록:

- 프런트엔드: 87개 파일, 680개 테스트 통과. TypeScript 검사와 Vite 빌드 통과. 기존 번들 크기 경고는 남아 있다.
- Rust library: 535개 통과, 14개 선택 실행 검사 제외, 실패 없음. 이 중 streaming 84개에는 원격 IPC 차단·로컬 IPC 유지·확장 경로·저장 복구 검사가 포함된다.
- 실제 WebView2 합성 영상/음성 입력으로 운영 녹화 스크립트와 네이티브 메시지·디스크 저장 경로를 검증했다. 약 15초 및 4초의 독립 WebM 파일 2개가 마무리되고 재개방 시 저널에서 복구됐다.
- 두 파일을 각각 새로운 HTML video에서 재생하여 640×360 영상 프레임과 440 Hz 합성 입력에 대응하는 음성 신호를 확인했다. 각 파일 시작 부분의 독립 디코딩 검사이며 전체 프레임 연속성·탐색성 검증은 아니다.
- 사용자가 지정한 공개 채널을 격리 프로필에서 열고, 검증 예제의 명시적 `--standard-quality` 옵션으로 일반 화질 선택을 한 차례 수행했다. 실제 영상 853×480, readyState 4, paused=false, 재생 시간·디코딩 프레임 증가, captureStream API 존재 및 Atsumi 네이티브 ready=true를 확인했다.
- 해당 공식 페이지의 원격 Tauri 내부 IPC 차단도 확인했다. 로그인·계정 쿠키 복사·실방송 녹화·확장 설치는 수행하지 않았다.
- 실제 방송의 녹화 영상/음성, 로그인·고화질/그리드·치트키/타임머신, 공식 Chrome 대비 지연 및 수시간 연속 저장은 아직 검증하지 않았다. 실제 방송 captureStream 성공 여부도 사용자가 녹화를 시작할 때 확인한다.
- 검증은 임시 카탈로그·프로필·합성 녹화 파일을 사용했고, 실사용 DB와 기존 다운로드/녹화 파일은 열거나 변경하지 않았다.
