# Atsumi 확장 구조 명세

상태: 1차 경계 리팩토링. CHZZK 구현 전 준비 단계.

## 목적과 범위

새 플랫폼을 추가하거나 외부 API가 변경될 때 기존 기능의 수정 범위를 제한한다.
모듈화는 성능 개선이나 프로세스 장애 격리와 같지 않다. 각각 별도로 검증한다.
이번 작업은 기존 동작을 보존하는 프론트엔드 경계 정리이며, 다운로드·병합·중복 판정 규칙,
Rust 작업 실행, IPC 이름, DB 스키마, 파일 경로, 저장된 설정 키는 변경하지 않는다.
CHZZK 메뉴, 연결, 녹화기 또는 사용되지 않는 범용 플러그인 프레임워크는 추가하지 않는다.

## 소유권과 의존 방향

- `src/App.tsx`: 실제 서비스와 기능을 연결하는 composition root. 플랫폼별 작업 로직을 갖지 않는다.
- `src/app/`: 공통 모드 선택, 메뉴 정의, 공통 화면 상태, 설정 저장 서비스,
  토스트, 프라이버시 표시, 업데이트, 튜토리얼, 창 위치, 안전한 종료 수명주기.
  Hitomi/Danbooru 화면이나 갤러리 선택·검색 reducer를 가져오지 않는다.
- `src/features/hitomi/`: 기존 갤러리 작업의 상태·구독·탐색·검토를 소유하는 지속 실행 기능.
  현재 화면의 표시 여부와 기능 상태의 보존 여부를 구분한다.
- `src/components/DanbooruWorkspace.tsx`: 기존 Danbooru 탐색·상세·다운로드 화면 및 상태.
  좁은 Danbooru API와 공통 화면 콜백만 전달받는다. 폴더 이동 자체는 필수가 아니다.
- `src/api/featureClients.ts`: 기능에 실제 필요한 메서드만 노출하는 어댑터.
  Tauri와 브라우저 mock은 기존 transport를 유지한다.
- 기존 `components`, `state`, `hooks`: 이전 위치와 export를 가능한 한 보존한다.
  갤러리 전용 컴포넌트가 이 폴더에 있다는 이유로 방송 기능이 재사용해서는 안 된다.

공통 앱 → 구체 기능의 연결은 App에서만 한다. 기능 → 다른 기능 내부 상태의 직접 접근은 금지한다.
기능 → 명시적인 공통 서비스 사용은 허용한다. 저장소 인터페이스가 존재하더라도
GalleryId/page/hash를 전제하는 계약은 갤러리 도메인의 계약이다.

## 1차 구현 계약

### 모드 등록

`workspaceRegistry`가 현재 지원 모드의 ID, 표시명, 설명, 메뉴, 아이콘, 배지 연결의 기준이다.
ContentSource는 registry에서 유도한다. 저장된 알 수 없는 모드는 Hitomi로 안전하게 복원한다.
저장 키 `atsumi.content-source.v1`와 기존 두 모드의 문구·메뉴·동작은 유지한다.
App은 각 등록 ID에 대응하는 화면을 명시적으로 연결한다. 새 모드 등록만으로 화면이 자동 구현되지는 않는다.

### 공통 화면과 Hitomi 상태

AppShell이 모드, 사이드바 접힘, 설정/활동/종료의 열림 상태 및 공통 서비스를 소유한다.
갤러리 reducer는 검색, 정렬, 선택, 상세 탭, 갤러리 검토 열림 상태만 소유한다.
HitomiFeature는 모드 전환으로 unmount하지 않는다. 기존 구독·자동 분류·세션 캐시가
화면 전환만으로 사라지거나 중복 시작되지 않아야 한다. 비활성 화면의 DOM과 단축키는 활성화하지 않는다.
이것은 앱 프로세스 재시작 후 RAM 상태를 복구한다는 의미가 아니다.

### API와 설정

Danbooru에는 runtime과 사용하는 Danbooru API만 가진 facade를 전달한다.
facade는 원본 메서드의 this를 보존하며, transport를 복제하거나 별도 상태 저장소를 만들지 않는다.
공통 설정 구독·저장은 앱에 한 번만 둔다. 기능에는 필요한 설정값 또는 기능별 projection을 전달한다.
기존 평면 SettingsSnapshot과 revision 충돌 처리는 유지한다. 논리적 소유권 분리와 DB 분리는 별개다.
목록 표시 설정의 대기 큐도 AppShell이 소유한다. 진행 중 저장 이후의 patch는 병합하되
동일 항목은 마지막 값을 사용한다. 개별 요청 실패가 뒤의 저장 요청을 막지 않으며,
모드 전환은 큐를 폐기하지 않는다. API 교체/앱 unmount 후 오래된 응답은 후속 저장을 시작하지 않는다.

### 종료 및 비동기 수명주기

종료 확인은 갤러리 선택 상태에 의존하지 않는 앱 서비스이다. 기존 작업 fingerprint 확인,
작업 변경 시 재확인, 상태 불명 시 재조회 후 명시적인 강제 종료 선택을 유지한다.
모드 전환으로 종료 요청 구독이 재시작되어서는 안 된다. unmount 이후 도착한 구독은 즉시 해제하고,
오래된 조회 응답이 새 대화상자 상태를 덮지 못하게 한다.

### 명시적으로 남겨 둔 이행 경계

현재 활동창은 갤러리 자동 분류의 상세 검토·복원과 Danbooru 세션 알림을 함께 보여준다.
현재 설정창도 갤러리 유지보수·제외 복원을 함께 제공한다. 이를 이번 작업에서 범용 이벤트 모델로
한꺼번에 바꾸면 기존 검토/복원 동작을 흔들 수 있으므로 HitomiFeature의 legacy 통합으로 유지한다.
App에는 표시 정보와 동작 콜백만 전달한다. 미래의 방송 작업을 GalleryId나 이 legacy 활동 모델에 넣지 않는다.
갤러리 즐겨찾기의 현행 Hitomi/Danbooru 공유 의미도 변경하지 않는다. 방송 채널 즐겨찾기는 별도 키가 필요하다.
HitomiFeature의 내부 hook/저장소 추가 분리는 후속 단계이며, 큰 파일을 이동했다는 이유로 완료로 보지 않는다.

## 방송 기능의 목표 구조 — 아직 구현하지 않음

### 구성

1. StreamingWorkspace: 채널 선택, 플레이어, 녹화 조작, 채팅·저장 목록 UI.
2. RecordingService: 녹화 세션의 생성·조회·정지·복구와 권한/정책 확인.
3. RecordingEngine: 영상 수신, 디스크 조각 확정, 재연결, 로컬 재생 공급, 채팅 시간축 관리.
4. ProviderAdapter(CHZZK 등): 인증과 플랫폼 API/전송/채팅 형식을 해석한다.
5. RecordingRepository/SegmentStore: 세션 상태, 복구 인덱스, 확정된 영상 조각, 채팅 기록을 보존한다.

공통 녹화기는 CHZZK JSON 필드나 임의 플랫폼 URL을 알지 않는다.
어댑터는 저장 DB나 React 화면을 직접 변경하지 않는다. 초기에는 CHZZK와 테스트 입력으로 경계를 검증하고,
두 번째 실제 플랫폼을 추가할 때 확인된 공통점만 추출한다.

### 최소 데이터와 기능 계약

- 콘텐츠 식별자: `{ provider, externalId }`. 녹화 실행은 별도 recordingSessionId를 사용한다.
- 기능 지원 여부: live/video/chat/seek 등 지원 범위와 미지원 사유를 명시한다.
  API·권한·정책상 미지원은 반복 재시도로 숨기지 않는다.
- 녹화 상태: 준비, 수신, 재연결, 마무리, 완료, 실패, 사용자 중지.
  영상 상태와 채팅 연결 상태는 분리한다. 무한 방송에 가짜 완료율을 표시하지 않는다.
- 영상 조각: 세션, 순서, 미디어 시간 범위, 파일 경로, 확정 상태, discontinuity를 기록한다.
- 채팅: 가능한 서버 메시지 ID/시각, 수신 시각, 표시용 정규화 데이터 및 시간축 대응을 기록한다.
  재연결 중 누락을 성공으로 꾸미지 않고 구간/오차를 표시한다.
- 명령: 시작/정지/재연결을 중복 수신해도 녹화나 파일 확정을 중복 실행하지 않는다.
- 조회/이벤트: 재접속 시 snapshot으로 상태를 복원하고 이후 이벤트를 합친다.
  IPC에는 버전·세션 ID·순서를 포함하고, 이전 UI의 오래된 결과가 새 세션을 덮지 못하게 한다.

### 단일 수신과 내구성

허용된 원본 영상은 한 번 외부 수신하고 확정된 로컬 조각을 저장과 플레이어가 공유한다.
공식 웹 플레이어와 별도 녹화기를 함께 실행하고 트래픽을 공유한다고 주장하지 않는다.
UI 새로고침은 녹화를 시작/중지하는 명령이 아니다. UI는 실행 중 세션에 다시 연결한다.
앱 본체 장애에도 녹화를 계속하려면 독립된 녹화 프로세스의 수명·재연결·중복 실행 방지가 필요하다.
단순 worker thread 또는 자식 프로세스 생성만으로 독립 수명이 보장되지는 않는다.
강제 종료 시 이미 확정한 조각을 보존하고, 미확정 마지막 조각의 손실 가능성을 명시한다.
전원 손실 무손실 보장은 별도의 파일시스템/flush 검증 없이 제공하지 않는다.

### 자원·보안 경계

녹화는 RAM 무제한 누적 대신 제한된 메모리 큐와 디스크 기반 저장을 사용한다.
영상 확정 작업, 갤러리 다운로드, 해시/중복 검사는 작업별 동시성·대기열·디스크 여유 공간을 관리한다.
필수 실시간 수신과 부가 작업의 우선순위를 구분하되 측정 없이 성능 향상을 약속하지 않는다.
로컬 플레이어 접근은 loopback 및 세션별 권한으로 제한하고, 인증정보·URL 토큰은 로그에 남기지 않는다.
서비스별 권한/약관과 DRM 제약은 연결 전 별도로 확인한다. 이 구조는 보호조치 우회를 위한 계약이 아니다.

## 검증과 후속 단계

1차: registry/저장 복원, 좁은 API, 앱 종료의 fake API 테스트, 공통 상태와 갤러리 상태 경계 테스트,
모드 왕복 후 탐색 데이터 유지, 비활성 Hitomi의 다운로드 이벤트 수신, 기존 App 회귀 테스트를 통과한다.
타입 검사와 프론트엔드 프로덕션 번들을 검증한다. 기존 Rust 변경은 이 리팩토링의 성과로 주장하지 않는다.

후속: legacy 활동/설정 통합을 section/provider 단위로 분리한다. 공통 활동은
source, jobId, label, status, timestamp, 지원 action과 상세 열기 콜백 정도만 공유하고 판정 규칙은 기능에 남긴다.
그 다음 가짜 방송 입력으로 끊김/저장 공간 부족/중복 명령/UI 재접속/프로세스 중단 복구를 먼저 검증한다.
실제 CHZZK 연결 후 장시간 녹화와 채팅 동기화, 단일 외부 수신량을 실측한다.

DB migration·방송 worker 도입은 별도 변경으로 검토한다. 전체 데이터 재분류, 실사용 파일 이동,
전체 해시 재검사, 릴리즈·커밋·푸시는 이번 구조 정리의 일부가 아니다.

## 1차 검증 결과

- 프론트엔드 전체: 75개 테스트 파일, 557개 테스트 통과.
- app/node TypeScript 검사 통과, Vite 프로덕션 빌드 성공.
- 공통 앱 단독 fake API 테스트, 설정 저장 큐와 종료 수명주기 경쟁 조건,
  모드 왕복 시 데이터 재요청/작업 취소/구독 중복 없음, 비활성 Hitomi의 다운로드 이벤트 수신을 검증했다.
- 주요 직접 모듈 의존 방향은 architectureBoundaries 테스트로 고정했다.
- 프로덕션 JS 번들은 약 845 kB(압축 전)이며 500 kB 초과 경고가 남는다.
  코드 분할, 실제 앱의 장시간 성능 측정, 녹화 프로세스 장애 복구는 이번 완료 범위가 아니다.
- Rust 소스와 실사용 DB/다운로드 파일은 이번 리팩토링에서 변경하지 않았으며 Rust 전체 검사는 재실행하지 않았다.

검증 명령(연결된 node_modules의 외부 임시 캐시 쓰기를 피하는 옵션 사용):

```powershell
./tools/run_frontend.ps1 test --configLoader runner --cache=false
node node_modules/typescript/bin/tsc --project tsconfig.app.json --noEmit --incremental false
node node_modules/typescript/bin/tsc --project tsconfig.node.json --noEmit --incremental false
node node_modules/vite/bin/vite.js build --configLoader runner
git diff --check
```

## 후속 구현: CHZZK 1차 (2026-09-10)

위의 1차 결과는 방송 기능 추가 전 구조 정리의 기록이다. 이후 CHZZK 전용 workspace와
StreamingApi, Rust 수신·채팅·저장 서비스 및 로컬 HLS 재생을 추가했다.
갤러리 계약과 DB migration을 재사용하지 않고 별도 파일 인덱스를 사용한다.
앱 종료·트레이·업데이트에는 녹화 활성 상태와 안전한 종료 장벽만 연결했다.

현재 provider는 CHZZK 하나이며, 다른 플랫폼까지 동작하는 범용 플러그인 시스템을 구현했다는 뜻은 아니다.
두 번째 플랫폼 추가 시 실제 공통점에 맞춰 어댑터 계약을 추출한다. 기능 범위, 저장 형식,
장애 시 보존 한계와 실제 연결 검증은 [CHZZK 명세](CHZZK.md)를 기준으로 한다.
