# CHZZK 녹화 중단·프로필·영상 전용 정리 (2026-09-20)

## 범위

- 실제 녹화 내용이 끊겨 빠지는 문제를 조사했다. 화면 잘림/플레이어 크기 변경은 이번 작업 대상이 아니다.
- 사용자의 후속 지시대로 **1GB 미만 녹화의 영상 파일만** 영구 삭제한다. 녹화 폴더, 오류, 채팅, 프로필, 시간표, 미완성 시간표, 병합 근거는 보존한다.
- 같은 방송 묶기는 아래 설계 제안이다. 이번에 서로 다른 원본을 물리적으로 합치거나, 추정만으로 과거 기록을 같은 방송으로 확정하지 않는다.
- 커밋·푸시·릴리즈·앱 자동 실행은 하지 않는다.

과거 다수 기록은 종료 이유가 일반적인 “녹화 중단”으로만 남아 있어 개별 원인을 확정할 수 없다. 이번 전송 재시도는 확인된 취약 경로의 보강이며, 과거의 모든 중단이 큐 포화 때문이었다는 뜻은 아니다. 이미 수신하지 못한 영상을 복구하지도 않는다.

공식 플레이어가 수신 자체를 건너뛰거나 소스를 교체하는 문제는 전달 재시도만으로 완전히 해결할 수 없다. 플레이어 수신과 시청 분리, 원본 시간축 단절 이후 재동기화는 별도 검증이 필요하다. 기존에 사용자가 지정한 “원본 저장·배속부터 검증하고 수신 분리는 별도 검토” 범위를 유지한다.

## 영상만 정리하는 방식

`tools/chzzk_video_only_cleanup.ps1`은 Plan/Apply를 분리한다.

1. 앱 종료, 카탈로그 ID, 절대 경로, 링크/재분석 지점, 기록 상태를 확인한다.
2. 1GB는 1,000,000,000바이트로 계산한다. 확정 영상+미완성 영상과 병합본 중 큰 값을 기준으로 한다. 큰 녹화 안의 작은 조각은 대상이 아니다.
3. 해당 녹화 루트의 `segment-<index>.mp4/webm`, `merged-<id>.mp4/webm` 및 그 영상의 `.partial`만 허용한다. `.timeline.jsonl.partial`은 삭제하지 않는다.
4. 계획 이후 파일/카탈로그가 바뀌면 거부한다. 카탈로그·시작 캐시·현재 개발 실행 로그를 별도로 백업한다.
5. 카탈로그에 `mediaRemovedAt`을 먼저 저장하여, 중간 종료 후에도 의도적 삭제를 오류로 오인하지 않게 한다. 원본 `recording.json`과 오류 문구는 수정하지 않는다.
6. 영상 파일별 삭제 내역을 기록하고, 보존 파일의 크기/수정 시각 및 비영상 파일 SHA-256을 대조한다. **대형 영상 내용은 해시 검사하지 않는다.**

정리된 기록은 보관함의 접힌 **영상 정리 기록 · 로그 보존**에 별도 표시한다. 한 번에 24개씩 펼치며, 영상 재생·자동 병합·구간 병합·원본 청소는 차단한다. 폴더 열기와 당시 오류 확인은 유지한다.

실제 계획: 226개 기록 중 영상이 있는 181개, 영상 파일 393개, 37,155,981,918바이트. 영상이 없었던 실패 45개도 진단 기록으로 보존. 1GB 이상 30개 녹화는 그대로 둔다.

## 같은 방송으로 묶기 제안

### 확정 묶음: 채널 ID + 방송 회차 ID

- CHZZK의 `liveId`를 저장한 `broadcastKey`가 같으면 하나의 방송 카드에 묶는다.
- 제목 변경, 자정 통과, 앱 재실행, 수신 오류 후 재연결은 같은 회차 ID인 한 카드를 나누지 않는다.
- 실제 종료 후 다시 켜서 회차 ID가 바뀌었다면 별도 방송으로 둔다. 같은 날이거나 제목이 비슷하다는 이유만으로 자동 합치지 않는다.
- 1부·2부를 사용자가 함께 보고 싶으면 별도 상위 **방송 묶음**에 수동 연결한다. 이때 각 회차 ID는 보존한다.

### 하위 구간: 원본 녹화 단위

상위 카드는 채널·방송 제목·시작 시각·저장 분량·누락 경고를 보여준다. 펼치면 각 녹화 구간의 시작/끝/종료 사유/파일이 나온다. 재생은 구간을 이어갈 수 있지만 없는 구간은 “미녹화 03:20”처럼 표시한다. 녹화 길이를 방송 길이로 오인하지 않도록 저장 분량과 방송 시간축을 구분한다.

기존 파일을 즉시 하나로 재인코딩하거나 로그를 합치지 않는다. 상위 그룹은 참조 목록이고 하위 원본은 그대로다. 삭제·복구·나중에 병합·채팅 검색에서 원본의 출처를 추적할 수 있다.

### 과거 ID 없는 기록

현재 256개 중 225개는 `broadcastKey`가 없다. 날짜/제목으로 일괄 소급 확정하면 오분류 위험이 크다. 같은 채널에서 저장된 `serverTime - broadcastOffsetSeconds`로 추정한 방송 시작 시각, 녹화 구간 사이의 공백, 제목 흐름을 조합해 **추천 묶음**만 만든다. 여러 시점의 표본이 일치해야 하며, 업타임 자료가 없거나 충돌하면 단독 기록을 유지한다. 사용자의 확인으로 묶고, 언제든 해제할 수 있어야 한다.

## 검증과 남은 확인

- 녹화 전달·보관함·프로필·자동 녹화 프런트엔드 테스트.
- 영상 제거 표시가 오래된 시작 캐시보다 우선하며, 오류/채팅/시간표를 다시 쓰지 않는 저장소 테스트.
- 프로필 64개 초과 저장, 과거 이름 유지, 다른 이미지로 잘못 복구하지 않는 테스트.
- 임시 폴더에서 영상 전용 삭제, 미완성 시간표 보존, 큰 녹화 보호, 재실행, 오래된 계획 거부 테스트.
- TypeScript 및 로컬 개발 빌드. 실제 방송의 장시간 연속 녹화는 이번 테스트로 보장하지 않는다. 사용자 설정을 유지하기 위해 앱을 임의로 켜 자동 녹화를 시작하지 않는다.
- 최종 결과: 스트리밍 Rust 테스트 319개 통과/6개 사전 지정 제외, 프런트엔드 테스트 118개 통과, TypeScript·프런트엔드 빌드·개발 실행 파일 빌드 성공. 영상 전용 정리 스크립트의 임시 데이터 테스트 통과.
